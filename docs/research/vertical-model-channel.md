打分进程（输入法）从来就是 b、c、d 的样子，但它的请求本来就是"用户在等"、很短，问题不显。嵌入和 PII 检查不一样：有大批后台工作，又有要快的用户请求，两种混在同一个进程上。

## 2. 原则

1. **引擎和专用模型是不同的资源，分开记账。** 引擎的后台名额是为了"后台生成别占着底座、能被打断"设的；专用模型各有自己的进程，和引擎之间争的只有 GPU 时间和内存。
2. **"交互中"的意思不变：用户在用这台机器。** 用户在等的专用模型请求也算交互，但**不打断**引擎上的后台——它根本不用引擎，打断只会白扔别人做了一半的工作。
3. **同一个专用模型进程里，用户在等的请求插队。** 插队靠把后台批切小，不靠在模型里中途取消（MLX 一次前向不能中断）。
4. **契约不变。** 配件照旧一次发 32 条，切小和排队都在主控里做；对外只加不改。
5. **业务逻辑归工具。** PII 的阈值、合并、路由判断留在 gateway；主控只给模型的原始输出（ARCHITECTURE：推理归主控，业务逻辑归各工具）。

## 3. 方案

### 3.1 记账：每个专用模型一条"通道"

派发器在引擎的后台名额之外，给每个专用模型加一条**通道**（lane）：

- 每条通道有自己的"后台正在跑"标记和自己的功耗间歇，按这条通道上后台工作的用时算（倍数同 `POWER_COOLDOWN`）。
- 嵌入的后台请求只看自己的通道：引擎上有后台生成在跑不挡它，它在跑也不挡引擎上的后台；功耗间歇也只歇自己的通道。
- 全机的条件照旧对所有通道生效：用电池、低电量、过热、内存压力、交互中（交互中的含义见 3.2）、16 GB 档的安静时刻。
- `busy` 的 `reason` 加一个 `lane_busy`（只加不改），给 `retry_after_ms`。
- 配件那边要照 `retry_after_ms` 原地等完再发，不能把功耗间歇当成被拒、整件退回队列：digup 10-19 就踩过（一个文件要发几个请求时，第二个请求总被间歇挡回，空转 799 轮；73eddf2 已修）。要在 V1 §8 的配件义务里写明这一条，邮件助手一次发多个后台请求时也要核一下。

**要负责人定（Q1）**：两条通道同时跑后台，后台总的 GPU 占用最多是现在的两倍（均衡档本来是"跑多久歇多久"，约 50%）。
- 方案 A（推荐先做）：通道各自歇，不合计。嵌入一批短文字的 GPU 时间是零点几秒级（实测均衡档 32 段短文约 0.36 s），叠加的时间短；先做简单的，看试用里风扇和电量。
- 方案 B：全机一个"后台占空比"预算（例如 60 s 窗口里均衡档合计 ≤ 50%、安静档 ≤ 25%），所有通道和引擎共用。更守规矩，但每条通道的接纳都要看全局账，代码和测试多一截。

### 3.2 用户在等的专用模型请求

| 请求 | 现在 | 方案 |
|---|---|---|
| 输入法打分、联想 | 记"刚打过字"（K 分钟窗口），打断引擎上的后台 | **不变**（打字要的是底座让 GPU，这条规则是为它定的） |
| 搜索查询（嵌入，用户在等） | 打断引擎上的后台 + 交互中 60 s | 只记**交互中**，不打断；在自己的通道里插队（3.3） |
| PII 检查 | （还没接） | **待定，等接入决定。**总是用户在等（gateway 只查要上云的用户请求，后台请求在查之前就留本机）。只记交互中、不打断引擎上的后台；先实测和后台 prefill 争 GPU 时的延迟，p90 超过 1 s 再改成打断（Q3，见 3.5） |

**要负责人定（Q2）**：一次搜索算不算"交互中"60 s（这 60 s 里引擎上不接新的后台请求）。推荐算：用户在搜索就是在用机器，和别的"用户在等"一样；如果试用里觉得邮件后台被搜索挡得太多，再给专用模型单设一个更短的窗口（比如 15 s）。

### 3.3 优先通道：主控切批、用户请求插队

- 主控在每个专用模型进程前面放一个**两级队列**（用户在等 > 后台），工作进程照旧一次只做一件事。
- 后台请求在主控里**切成小块**再交给进程：每块不超过任务参数 `bg_chunk_items`（建议 8 条）和 `bg_chunk_tokens`（按 token 估算的上限）。块与块之间先看用户在等的队列，有就先做它。所以用户请求最坏只等一块。
- 块的大小按"一块在这一档最慢的机器上不超过约 150 ms"定，**要实测**：每档用 8 条 × 2048 token 的最长文档量一次（M1 16 GB、M3 Pro 36 GB 两台）。量出来超了就把 `bg_chunk_items` 调小。
- 切块对配件看不见：请求还是 32 条，答复还是一次 32 个向量。整批的总用时算进通道的功耗间歇。
- 用户在等的请求不切（查询通常就 1 条）；超过一块大小的照样一次做完。
- 后台块做到一半时，如果全机转为暂停（过热、内存压力），剩下的块不做，答 `paused`，已算的那部分不返回（配件整批重发；嵌入是幂等的）。
- 不选的做法：
  - 再起一个专门给用户请求的进程：内存翻倍（嵌入带图片、声音时 phys_footprint 峰值约 3.9 GB），16 GB 档放不下。
  - 在工作进程里中途取消：MLX 一次前向停不下来；在进程里切块、读 stdin 上的取消信号，和主控切块效果一样，但协议更复杂。

### 3.4 内存：专用模型进程的生命周期（#5 审阅第 4 条）

| 事 | 方案 | 嵌入分到档之前 |
|---|---|---|
| 启动前查内存 | 起进程前用 `fits_memory`（Metal 上限 − 现在 wired ≥ 这个模型的 `wired_gb` + 余量）；放不下：后台答 `paused`（memory），用户在等答 `needs_user`（和底座一样带 occupants） | **必须** |
| `wired_gb` 实测 | 量 `phys_footprint`（加载后、跑过一批最长的输入后各一次），文字和带媒体两种模式分开记：配方里加 `wired_gb_media`。按 phys_footprint 的**峰值**记（RSS 不算 Metal 缓冲，会少算好几倍）。已有一组：digup 10-19 在 rc1 上带图片、声音建索引，33 次采样 2.2–3.9 GB，所以 `wired_gb_media` 先按 4 GB 估；文字模式还没量 | **必须** |
| 闲置停止 | 每个专用模型一个 `idle_stop_secs`（嵌入建议 600 s：建索引时一直有请求，不会停；用户搜索是零星的）。停了就不再从天花板里扣。用户在等的请求遇到没起的进程：主控起进程，**等它加载好**（嵌入约 2 s，最多等 `load_secs` × 3），不答 `not_ready` 让配件重试 | **必须** |
| 内存压力 | warn：这条通道的后台暂停（同引擎上的后台）。critical：进程空着就停掉；用户在等的请求做完再停。输入法的打分进程照现在的规则（DESIGN §5：critical 且卸掉底座后仍不够才停） | 16 GB 档之前必须；32/128 档可以后补 |
| 任务参数改了要重启 | `media`（收不收图片、声音）现在建进程时定死。配方或档变了（`tasks_version` 变）时，参数不同的进程停掉，下次请求按新参数起 | 开图片、声音之前必须（#5 审阅第 6 条后半） |

### 3.5 PII 模型要的接口和容量（待定，等接入决定）

> **待定，等接入决定。**10-19 晚定：PII-Tracer 是否接入待定，不排进 beta1。下面的接口、运行时、常驻和评测都只是接入时的参考，`tag` 类型和 `/v1/tag` 端点现在不做。

数字来自 luoke-integration 会话（gateway 作者）2026-10-19 的答复，实测在 M3 Pro 36 GB 上，gateway 配置 C；数据是合成数据和 luoke-mail 的虚构示例收件箱，提示词用 luoke-mail 0.13.2 的。

**模型**：HF `perplexity-ai/PII-Tracer` @ d25c16f，MIT。

- 编码器是 transformers 的 `Qwen3Model`，但注意力是**双向**的（`is_causal=False`）：28 层，hidden 1024，intermediate 3072，16 个注意力头、8 个 KV 头，head_dim 128，词表 151,936，约 0.6B 参数。权重 bf16，1.19 GB（safetensors；模型代码 `modeling_pii_masking.py`，10-15 审过，没有网络、exec、pickle）。
- `max_position_embeddings` 是 32,768，但模型的 `predict()` 默认 `max_seq_len` 4,096，超了就截断。
- 两个头：
  - 每个 token 一组 37 个标签的分数（O 加 9 类 × BIOES；9 类是 person、email、phone、address、url、date、account_number、secret、other_pii），再用模型自带的受约束 BIOES Viterbi 解码成片段；
  - 整段平均池化 → 线性 → sigmoid 的一个"敏感度"，0–1。
- 片段的分数：单 token 的片段是那个 token logit 的 sigmoid；多 token 的是 logit 平均后再 sigmoid。gateway 现在**不设分数阈值**，解码出来的片段全用。
- gateway 现在的用法：
  - 所有消息（含系统提示词）拼成一段文字，按空行切段，每段一次前向；超过 4,096 token 的段按 4,096 开窗、重叠一半（2,048），窗口里重复的片段去重；
  - 敏感度落在灰区（0.5–0.8）就留本机；
  - 运行时是 transformers 5.19.0 + torch 2.14.1（至少要 transformers 5.2 才能跑双向 Qwen3），MPS，bf16；没有 MPS 时 CPU fp32。
  - 后处理都在 gateway：类别定级 L1–L4、去掉边上的括号和标点、去敬称、地址特征、订单号和运单号不算账号、和规则及联系人的结果合并、全文传播。

**谁调、多频繁**：

- **只有"用户在等"的请求才查**：后台请求在查之前就被 gateway 的 R11 留在本机，不调这个任务。
- 用户每点一次（分析一封、起草一封、页面开着时清理或退订一批）查一次。现在是一次请求 5–11 次前向。
- 实际量：第二次试用约 38 小时里只有 2 次；第一次试用 43 分钟里有 40 次，大多是连点清理。容量按"连点清理"的突发定：每批间隔几秒到十几秒，每批约 1.3k token。

**输入多大、现在多慢**（模型时间）：

| 场景 | token 中位 / 最大 | 段数 中位 / 最大 | 最长一段 | p50 / p90 / 最大 |
|---|---|---|---|---|
| 单封分析（40 封） | 725 / 759 | 8 / 11 | 433 | 362 / 386 / 422 ms |
| 起草回复（40 封） | 263 / 297 | 5 / 8 | 125 | 171 / 198 / 236 ms |
| 清理一批（25 封，6 批） | 1,304 / 1,428 | 7 | 1,066 | 530 / 587 / 658 ms |
| 退订一批（10 个，5 批） | 525 / 629 | 5 | 413 | 255 / 277 / 327 ms |
| 人造长段（10,388 token，3 个窗口） | — | 1 | 10,388 | 4,667 ms |

- 每次前向的固定开销约 45 ms。一封要 8 次前向，所以合成**一次批量前向**是最大的收益。
- 大部分 token 是工具自己的系统提示词（带"关于你"，要一起查）。最长取决于调用方任务的字符上限。
- 字符数（不跑模型数的）：单封分析总长 p50 1,437、最大 1,623 字符，最长一段 854；起草 463 / 649，最长一段 266；清理一批 2,816 / 2,891，最长一段 2,198；退订一批 1,304 / 1,580，最长一段 1,134。真实长邮件没测过。
- 冷启动：加载约 5 s（模型文件在磁盘缓存里时；冷磁盘不知道）。
- **内存没量过**：权重 1.19 GB，另加激活和运行时。gateway 的试用进程 10-19 16:59 随回滚停了，没法补测；MLX 版要自己量（同 3.4 的 `wired_gb` 实测）。
- 全部实测在一台 MacBook Pro（M3 Pro，36 GB）上，MPS bf16，模型已预热。库模式 p50 124 ms、p90 335 ms 是 10-16 LEPB tune 集 3,948 条只分析正文、整次分析（规则 + 模型 + 合并）的时间；配置 C 每封多约 400 ms 那次测试主控也在跑，数字偏保守。

**延迟要求**：查完才上云，用户一直在等。

- 附加延迟目标：p50 ≤ 0.5 s，p90 ≤ 1 s，最慢 2 s。
- 超过 5 s，或者主控答 busy、not_ready、unsupported、engine_failed，gateway 就不发出去（fail closed），把原请求交给本机主控生成。
- 所以：不能排在任何后台工作后面，不能冷启动（5 s 就超时）。

**接口方案**：新任务类型 **`tag`**（标注）。不复用嵌入或打分：嵌入出向量，打分出语言模型的对数概率，都给不出每个 token 的标签和字符位置。

- 请求：`POST /tasks/<任务名>/v1/tag`，`{"texts": ["段落1", …]}`。一次请求的所有段一起送；等级看 `X-Luoke-Priority`，实际总是用户在等。
- 答复：`{"spans": [[{"start", "end", "label", "score"}, …], …], "sensitivity": [每段一个 0–1], "label_set", "model", "ms"}`。
  - `start`、`end` 是**原文的字符偏移**：分词、token 到字符的映射、BIOES Viterbi 解码都在主控里做，gateway 不碰 token；
  - `score` 是片段的分数；
  - 敏感度的灰区判断、合并、allow_terms、路由都留在 gateway（原则 5）。
- 长段：主控按任务参数 `window_tokens`（4,096）开窗、重叠一半，窗口间重复的片段去重，合并后按原文偏移返回（gateway 说放在主控或 gateway 都行；放主控，gateway 就完全不碰 token）。分数照模型的定义（sigmoid，多 token 取 logit 平均），主控不加阈值。总量超过任务参数 `max_total_tokens` 时答 `input_too_long`，gateway 照现在的 fail-closed 处理。
- **`label_set`**（例如 `"pii-tracer-bioes37/1"`）像嵌入的 `vector_space`：标签集或模型版本一变就加一，也算进 `tasks_version`。同一版本下同样的输入，输出必须一样（0 温度、确定性解码，评测里核对）。
- 只加不改：新端点、新 kind，不碰已有的。

**调度和常驻**：

- PII 的通道（3.1）只有用户在等的请求，没有后台块要切（3.3 不涉及），一次请求一次批量前向（按长度分桶补齐，免得短段跟着最长一段算）。
- 和嵌入、打分是不同的进程，互不排队。
- **和引擎争 GPU**：被它守护的请求是要上云的，所以引擎上的后台生成不会被那个请求打断（3.2 也定了不打断）。但 9B 后台 prefill 正在跑时，PII 的一次前向会变慢多少还不知道。
  - **要实测**：M1 16 GB 和 M3 Pro 36 GB 上，引擎跑后台 prefill 的同时测"清理一批"的 p90。
  - 如果 p90 超过 1 s，PII 检查改成和打分一样打断引擎上的后台（Q3）。
- **常驻**：只有用户打开 gateway 的云端路线时才需要它。
  - gateway 在云端路线打开期间持一个预热租约（DESIGN §5），主控据此加载并保持加载、不闲置停止；租约到期或路线关掉就停，不再从天花板里扣。
  - 内存压力规则同 3.4；16 GB 档上 1.2 GB 常驻要算进预算。
  - 起不来（`fits_memory` 不够）时答 `paused`（memory），gateway 照 fail-closed 留本机，不会泄露。

**运行时（风险最大的一条）**：主控的工作进程跑在引擎包自带的 Python 里，只有 mlx、mlx-lm、mlx-vlm，没有 torch。

- **推荐移植到 MLX**。
  - mlx-lm 已有 Qwen3 的实现，改成双向只是去掉因果掩码；两个头一个是线性层、一个是平均池化加线性层；Viterbi 解码用 numpy 就够。
  - 做法同嵌入：vendor 一份模型定义（标出处和许可证），权重转成 MLX 的 safetensors，由主控分发（ADR 0018）。
- 不起 torch 工作进程：PyTorch 加 transformers ≥ 5.2 要往引擎包里放上 GB 的东西，签名、公证、内存都跟着涨，还要多维护一个运行时。
- **对照测试**是放行条件：同一批输入，MLX 版和 gateway 现在的 transformers 版逐段比。
  - 测试集：LEPB tune 集 3,948 条，加上上面四种场景。
  - 片段：类型和起止完全一致的比例，门槛待定，建议 ≥ 99.5%。
  - 敏感度：相差 ≤ 0.01，而且灰区（0.5–0.8）判断不翻。
  - LEPB 的 L2/L3/L4 泄露仍为 0。
- 要验证的还有速度：一次批量前向能不能把"单封分析"的 362 ms 压到 0.5 s 典型、2 s 最慢的预算里还有余量（目标 p90 ≤ 300 ms），在 M1 上也量一次。

**评测**：发布评测用 LEPB（gateway 自带）。gateway 提出 LEPB 的离线大批量评测（库模式 3,948 条，在开发机上）可以照旧在 gateway 进程里直接加载模型跑，不经主控。这是开发工具不是产品里的运行实例，但和负责人"体系里没有脱离主控的运行实例"怎么对上要负责人确认（Q7）；不行就让评测也经实验室主控跑（3,948 条按 p50 约 0.3 s 算约 20 分钟）。

- 硬性条目：L2/L3/L4 泄露为 0；
- 分数：PERSON、ADDRESS 等的召回；
- 外加上面的对照测试。
- 和嵌入一样进评测表（3.6）。

**配件身份**：gateway 要有自己的清单和配方里的任务（例如 `gateway.pii`，kind `tag`），按配件接入契约（DESIGN §11）走。

### 3.6 发布流水线放行 digup（#5 审阅第 7 条）

照协调会话的建议：给嵌入配一条正式评测，不在流水线里开白名单。

- `tools/release_evals.json` 加 `digup.embed`：
  - 评测程序是主控自带的 `tools/embed_parity.py`（已有），对着实验室实例的 socket 跑；
  - 参考向量集从 digup 仓库读（`HubParityTests` 用的那份），版本号从 digup 的清单读。
- 结果解析：
  - 硬性条目 = 每一条参考向量的余弦都 ≥ 0.999（文字 5 条；开了图片、声音以后加媒体 4 条）；
  - 分数 = 过线的条数 / 总条数。
- 评测证据进 `verified`（digup 的版本）和支持台账（哪一档开）。流水线不用为"没有生成类评测的配件"开特例。
- PII 如果接入，用 LEPB 走同一条路（待定，等接入决定）。
