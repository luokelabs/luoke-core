# 远端引擎：局域网里另一台机器、或云端 GPU 上的模型

- **状态**：2026-10-13 负责人提出，当天定为"以后"（DESIGN §0 的以后清单）。v1 不做，这里记下取舍，免得将来重想。
- **负责人的问题**：local AI 能不能囊括"局域网里另一台算力更强的设备跑本地模型，通过网络访问"，再扩展到"租一个云端 GPU 跑自己部署的模型"。

## 结论

1. **架构上装得下，对外约定不用改。** 配件只认任务层的 socket，不知道模型在哪跑（ADR 0006：所有推理经主控）。远端引擎是主控内部多一条路；改的是派发和预算（远端没有本机共存的那些事——打字受影响、16 GB 装不下——换成网络延迟、可用性、断线重连）。
2. **打分任务留在本机。** 输入法一次打分几十毫秒，经不起一次网络往返；只有共享模型的生成任务值得转到远端。
3. **做法：主控对主控，不是主控直连远端 oMLX。** 远端那台也装螺壳主控，两台主控之间说话：Bonjour 发现、配对码、本机主控把共享模型的任务转给对方的任务层。这样配方、已验证版本、派发规则、隐私规则在远端照样成立，远端那台自己也能用；远端引擎的版本和模型仍由配方管。云端 GPU 就是同一套协议跑在 Tailscale 之类的网络上，由用户自己部署，实验室不运营、不代租，顶多出一份"怎么在云上装主控"的说明。
4. **产品边界**："家里那台大 Mac 给笔记本干活"和主控的比喻一致（一个家的主控，配件插上就用），进精品范围；租云端 GPU 要部署、密钥、账单，不是"不折腾的普通用户"的事，放在说明文档里让会折腾的人自己来。

## 隐私怎么说（2026-10-13 问：用户说"那就是我自己的环境"，我们能区分吗）

区分不了，也不该试图区分。主控验证不了一台远端机器归谁，局域网和云端对主控来说一样：一台配对过的主控。所以承诺要按主控**做什么**来写，不按机器**在哪**来写：

- 请求文字只发给**你自己配对过的主控**，传输加密；实验室和任何第三方看不到，主控也不记录。
- 配对是用户亲手做的一次动作（输配对码），从那以后"那台机器是我的"就是用户自己的陈述，主控照此办，不再追问。
- 主控把"这次是哪台机器做的"写进答复的组合字段和状态灯，用户随时看得见；远端不在局域网时状态灯说明一下（这只是提示，判断不严格）。

V1 §9 那句"请求文字只在内存里"到那时改成"只在你配对的主控之间传输、只在内存里"。

## 要做的时候再定

- 发现与配对：Bonjour 服务名、配对码、证书钉住；多台远端怎么选（按档位、按空闲）。
- 派发：远端不可达时回退本机还是报 `task_unavailable`；两边配方版本不一致怎么办（以本机配方为准，远端只接它验证过的组合）。
- 远端的"用户在等"和"后台"：远端那台自己的用户也在用，两边的交互中怎么合并（远端主控自己判，本机只是一个调用方）。
