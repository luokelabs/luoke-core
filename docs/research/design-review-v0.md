# luoke-core 设计 v0 审查

> 注（2026-10-10）：文中的 jiu 已由螺壳输入法（luoke-ime）取代。本文是当时的审查记录，保留原样；现行的配件需求见 [accessory-requirements.md](accessory-requirements.md) 和螺壳顶层各配件的注册页。

> 设计审查（2026-10-09）：对 v0 文档做的五路审查（文档内矛盾、与现实矛盾、冗余、成本超前、分期），每条发现经独立反驳核实后汇总。这是建议，不是决定；哪些采纳由负责人决定。


## 总评

设计在原则上是自洽的：主控对用户可见，配件只说任务，配方封闭，每档一个底座，质量由实验室验证，只在本机运行，不需要管理员权限。这几条互相支撑，ADR 也大多给了理由。问题集中在三处：

1. **配方的数据模型锚在"底座 × 硬件档"上。**它装不下三种情况：维持期和回退期间同一档同时有两个底座；jiu 只用专用模型；引擎升级后需要回退。锚点应改成"组合 / 模型分配"。
2. **引擎层和现实对不上。**
   - ADR 0001 标着"已核实"的 oMLX 启动清单，实际会打开 SSD 缓存、扫描用户的 HF 缓存。
   - oMLX 自带的 memory guard 是另一套内存管理器，和主控的预算各管各的。
   - jiu 的 580 ms 要求和 16 GB 档"底座常驻、后台分拣"的设计基本互斥。
   - jiu 和 luoke-mail 的真实进程结构与接入方案不一致。
3. **全文没有分期。**换代、维持期、撤回、异步作业协议、后台入口、复用、社区测试者、统计非劣检验，都是按"大量陌生用户、多个配件"写满的。v1 实际只有一个用户、两个配件、三台机器。

---

## 一、矛盾

### 高

**1. 配方以"底座 × 硬件档"为锚，装不下同档两个底座，也装不下专用模型**
- **位置**：CONTEXT「底座」「任务」「任务参数」「已验证版本」「换代」；DESIGN §3（封闭、签名与版本、任务参数）、§5「8 GB 的 Mac」、§7 发布前必须验证、§8（维持期、保留旧底座、撤回）、§11 jiu；ADR 0004、0005、0008。
- **问题**：
  - CONTEXT 说每档只有"唯一一个"底座，参数按"任务 × 硬件档"定。但维持期、旧底座保留期、回退期间，同一档必然挂着两个底座。
  - 例：16 GB 档从 Bonsai 2 换成 Qwen3.5-9B。拒绝换代的用户也必须接受新配方，因为撤回清单在里面。可 (mail.triage, 16GB) 只有一个参数位，Bonsai 只能套用 9B 的参数（research A6 说的 JSON 截断），或者无参数可用。
  - jiu 只用专用模型，8 GB 档又不设底座。按"已验证版本 = 在某个底座上达到及格线"的定义，jiu 永远不能被安装。
  - jiu 的打分模型从 0.8B 换成 2B 不算"换代"。新配方带着 2B 的 τ 自动装上，而 2B 的下载要先征得同意，于是出现"配方已切、模型没下"的空档。
- **理由**：这是配方 schema 的主键，安装器、派发、证据展示都建在它上面。照字面实现，第一次换代就装不下维持期用户。
- **建议**：
  - 参数和证据的键改为"任务 × 模型分配（模型文件哈希）× 引擎版本"。硬件档下允许列多个模型条目，每条带角色：现役、维持中、已退役（仅供已装用户继续用）。
  - 改写术语：
    - CONTEXT「底座」改为"每档当前推荐的唯一底座"。
    - 「已验证版本」改为"在它的任务用到的每个现役模型分配上都达标"。
    - ADR 0008 和 §7 的"所有现役底座"改为"该配件用到的所有现役模型"。
    - 「任务参数」改为"随所用模型变化"。
    - 「任务」里"一套任务参数和一份证据"改为"在同一个模型上只有一套任务参数"。
  - 专用模型的更换并入换代流程：需要新模型的配方切换，必须和下载放进同一次征求同意。
  - §3 补一句：仍在配方中的退役条目不算"配方外"。

**2. ADR 0001 的 oMLX 锁定清单与 0.7.0 源码不符**
- **位置**：ADR 0001 Consequences；DESIGN §5「怎么用 oMLX」、§10「请求文字只留在内存」「本机边界·引擎」、§13.5；oMLX cli.py:355-368、1294-1300、283-298，settings.py:377、433-445、704。
- **问题**：
  - ADR 写"不传 --paged-ssd-cache-dir（SSD 前缀缓存默认关闭），在源码里核实过"。实际 `CacheSettings.enabled` 默认是 True，目录默认 {base_path}/cache，上限默认是可用空间的一半。照这份清单启动，由邮件正文和打字内容算出的 KV 块会落盘。本机 ~/.omlx/cache 现在已有 565 GB。
  - `hf_cache_enabled` 默认也是 True：主控的 oMLX 会扫描 ~/.cache/huggingface/hub，配方外的模型会出现在 /v1/models 里。
  - oMLX 默认写 logs/server.log 和 crash.log。§10 要求的"关闭 prompt 日志"，在启动参数里没有对应项。
- **理由**：
  - §10"请求文字及派生物不落盘"是 jiu 接入的核心承诺。ADR 标着"已核实"，实现时很可能被照抄。
  - interrupt-and-resume 里的前缀缓存数据（例如 27B 命中约 29%）是在开着 SSD 缓存的 oMLX 上测的，搬不到主控的配置上。
- **建议**：
  - 重写启动清单，关缓存三选一：`--no-cache`（代价是失去跨请求前缀缓存）；`hot_cache_only` 加 `hot_cache_max_size`（只放内存，需用标记字符串实测）；或 `OMLX_CACHE_ENABLED=false`。
  - 无论选哪种，都加 `--no-hf-cache`，启动时清掉 HF_HUB_CACHE、HF_HOME、OMLX_* 环境变量，并把 {base_path}/logs 纳入标记字符串测试。
  - "在源码里核实过"改为"启动清单随引擎版本逐条验证，作为配方里引擎条目的一部分"。
  - §13.5 的命中率改在主控实际采用的缓存配置下重测。

**3. 主控的内存预算和 oMLX 的 memory guard 是两套各管各的管理器**
- **位置**：DESIGN §6「内存」（从不硬挤、仍然加载、专用模型优先、安全底线）、§12「内存压力」；ADR 0001 Consequences；oMLX process_memory_enforcer.py:1745-1800，server.py:3479-3510，cli.py:1227-1238。
- **问题**：
  - memory guard 默认开着（balanced 档），天花板由它自己算，并把主控的专用模型进程、用户自己的 oMLX 一起算进去。超限时 load 和推理直接返回 507 或 400，load 接口没有强制加载的参数。
  - 硬压力下它调用 `abort_all_requests`，不分请求等级，"用户在等"的请求会一起被中止；它还会按 LRU 自己驱逐模型。luoke-mail 已经碰到过 400 "prefill memory guard" 和 507。
  - wired 上限在 sysctl 非零时取 min(sysctl, 它自己的天花板)，用的不是主控算出的预算。
- **理由**：§6 给用户的"仍然加载（可能会卡）"照样会被 oMLX 拒绝；"专用模型优先"只在主控自己的账本上成立。用户最后看到的是没法解释的 507。
- **建议**：
  - 用 `--memory-guard-gb` 把主控的预算传给 oMLX，作为它的天花板。
  - "仍然加载"写明实现方式：重启引擎换一个天花板，或用 `--memory-guard off`；做不到就删掉这个选项。
  - `abort_all` 和 LRU 驱逐计入 §12 的引擎故障。
  - §13 加一项实测：oMLX 和专用模型两个 MLX 进程并存时，oMLX 的天花板怎么变。

**4. 回退的单位是"旧底座"，不是"上一个组合"**
- **位置**：CONTEXT「回退」「撤回」；DESIGN §5「引擎版本属于配方」、§8 更新（自动安装引擎包、保留旧底座、撤回）、§12「引擎故障」；ADR 0001 Consequences；research A12。
- **问题**：
  - 引擎包在安静时刻自动安装，§8 却只保留旧底座。A12 原文是"旧底座和上一版引擎包一直保留"，写进 DESIGN 时丢了后半句。
  - 场景一：配方只把 oMLX 升到 0.7.1，在 M1 上反复崩溃、触发熔断。这次没有换代，也没有上一版引擎包，无处可回。
  - 场景二：撤回某个引擎版本时，"有保留着的旧底座就回退过去"无效，因为旧底座跑在同一个被撤回的引擎上。
  - 场景三：维持期满后底座 B 被撤回。旧底座 A 可能还在磁盘上（删除要用户点），回退后 A 会和只在 B 上验证过的配件版本一起跑。
- **理由**：撤回是设计里唯一不经同意的强制手段；ADR 0001 又说引擎升级"和换代一样"，引擎这一侧却没有回退路径。自动回退还会绕过 ADR 0008 的"只跑已验证的组合"。
- **建议**：
  - CONTEXT 引入"组合"一词（每档的模型文件 + 引擎版本），「回退」改为"退回保留着的上一个组合"。
  - §8 改为同时保留旧底座和上一版引擎包；只升级引擎时，也走"冒烟检查 → 失败就回退"。
  - 加一条总规则：任何回退都必须落在配方列为已验证的组合上，否则相关任务暂停。
  - "保留着的旧底座"限定为"保留期内，且维持期仍有效"。
  - v1 只需要引擎包这一部分，见超前第 2 条。

**5. jiu 的 580 ms 要求和 16 GB 档"底座常驻 + 后台分拣"基本互斥**
- **位置**：DESIGN §11 jiu 最后一条、§6「打断」「专用模型与后台让路」、§13 第 6 项；ADR 0006 Consequences；research jiu-现状.md、design-review-gaps C5、interrupt-and-resume §2(1)；oMLX server.py:2612、scheduler.py:1684。
- **问题**：
  - 580 ms 是 jiu 独占 GPU 时在 32 GB 测试机（基础款 M4）上测的。加上其他常驻模型服务后，中位数到了 1.6 s（C5）。
  - §6 只保证"不启动新的后台请求"。jiu 要等用户停手 0.35 s 才发请求，在那之前开始的后台 prefill 还在跑。
  - oMLX 打断一个请求，要先等约 2 s 的断开轮询，再等当前 prefill 块跑完。块的上限是 2048 token，主控无法配置。
  - GPU 争用和 jiu 的模型在哪个进程里跑无关，ADR 0006 是缓解手段，不需要改。32 GB 测试机的内存大小文档里没写，需要确认。
- **理由**：这决定了 16 GB 档能不能同时开 luoke-mail 和 jiu、后台让路要多激进、§5 的常驻怎么做，是 v1 最大的未知数。
- **建议**：
  - 把 §13.6 提为 v1 第 0 步。测量条件定为"底座常驻且后台 prefill 正在进行"，包括"prefill 中途被打断"的最坏情况，在 32 GB 测试机和 16 GB 测试机上测 p50 和 p90。
  - §6 准备两个备选：按会话让路（最近 N 分钟有打字就不启动后台 prefill）；16 GB 档限制后台 prompt 长度或分段提交。
  - 向 oMLX 提需求：prefill_step_size 可配置，或能按请求设置。
  - 如果坚持 580 ms，就明写"16 GB 档的后台工作只在安静时刻跑"。

**6. jiu 的真实结构和 §11、ADR 0007 的接入方案对不上**
- **位置**：DESIGN §11 jiu、§5「配件运行时」；ADR 0007 Consequences、ADR 0006；ime_eval/corrector/main.swift:282、608、801、905-906，corrector_service.py，run_eval.py:37-80，build_app.sh。
- **问题**：jiu 现在的结构是：纠.app（Swift）只管按键监听、辅助功能读写和菜单，用 /usr/bin/python3 启动 corrector_service.py；RIME 查询、词表保护、stepwise、τ 判断都在 Python 里。由此有几处对不上：
  - ADR 0007 的"Swift 用 Network 框架写 socket 客户端"连错了一端，真正要连任务层的是 Python 那一半。
  - "判断逻辑留在 jiu"意味着 jiu 也是 Python 配件，而 §5 的配件运行时只写了给 Python 配件用。
  - jiu 自己注册了 SMAppService 登录项（菜单里的"登录时启动"），§11 没删它，和"主控是唯一登录项"冲突。
  - import_material.py 也用 /usr/bin/python3。
  - librime 依赖 boost、leveldb、opencc 等，"静态链接"难做。
- **理由**：这决定 jiu 接入的工作量和延迟路径。如果移植到 Swift，是一次大改，88.5% 准确率和零改错都要重测。
- **建议**：
  - §11 二选一。推荐保留 Python 判断进程，用 `http.client` 子类连 UDS；Python 运行时的方案见超前第 8 条。
  - rime_probe 和 librime 作为签名的 helper 或 dylib 放进 Frameworks（参考 Squirrel 的做法），不写"静态链接"。
  - ADR 0007 的 Swift 客户端那句删掉，或改为"若移植到 Swift"。
  - §11 的删除清单加上"登录时启动"，并注销已注册的 SMAppService；import_material 改用新的运行时。

**7. §11 的"可选任务"和"每个任务都要交评测集"冲突**
- **位置**：DESIGN §7「评测」、§3「任务表跟着配方发」、§11 luoke-mail；CONTEXT「评测集」；ADR 0003、0008；research A7。
- **问题**：
  - luoke-mail 约 8 个任务里，只有分拣有评测（40 封）。
  - 按 §3 和 §7，没有判分规则的任务进不了配方，主控根本不会服务它；"可选"并不豁免评测。照字面执行，v1 的 luoke-mail 只剩分拣一个任务。
  - 反过来，如果"可选"允许没评测的任务进配方，就成了 ADR 0003 否决过的"未经评测"状态。
- **理由**：主要/可选本来只表示任务对配件有多重要，不该变成封闭配方的后门。这个问题开工第一天就会碰到。
- **建议**：
  - §7 和 §11 统一成一种说法：v1 只上线有评测集的任务。
  - 每个对外任务配一个 20–40 条的小评测集（含硬性条目），由 AI 代理补齐 luoke-mail 其余任务。
  - 暂时没有评测集的功能，先用非 AI 的做法或隐藏。
  - 删掉 §11 的"先标为可选任务"。

### 中

**8. 延迟到底是及格线还是"延迟要求"，速度的口径也不统一**
- **位置**：CONTEXT「及格线」「冒烟检查」；DESIGN §7「评测」「用户机器上」、§9「依据」、§11 jiu 最后一条、§12「引擎故障」；ADR 0008 Consequences。
- **问题**：
  - CONTEXT 和 §7 的三层及格线里没有延迟，§7 说延迟达不到只显示"较慢"；§11 却把"M4 p90 ≤ 580 ms"写进了及格线。
  - 例：jiu 1.1 在 M5 Max 上三层全过，在 M4 上 p90 是 610 ms。照 §11 不能发布，照 §7 已经验证。ADR 0008"一台机器跑完"的设想也测不了 M4。
  - 依据显示"每封约 2.5 秒（M5 Max 实测）"，M1 用户会同时看到它和本机实测的"较慢"数字。
- **理由**：这决定每个 jiu 版本的发布关卡是什么、要用几台机器。
- **建议**：
  - 延迟只保留"延迟要求"一种机制：实验室在自有最慢的机器（M1、基础款 M4）上把它当发布关卡；用户机器上用来提示"较慢"。
  - §11 那条改写为 jiu 打分任务的延迟要求。如果它本意只是"jiu 接入主控"的一次性验收，就写明。
  - 看门狗超时、"较慢"判断、界面上的速度，都用本机冒烟检查的实测记录；依据只写质量结论。

**9. 任务状态里混进了后台调度状态，"需要换代"也不在枚举里**
- **位置**：CONTEXT「任务状态」「请求等级」；DESIGN §4「同步与异步」、§6「功耗与电源」、§8 维持期与撤回、§9「任务状态」、§11 luoke-mail、§12「引擎故障」；research B1、B3。
- **问题**：
  - §9 把用电池、等内存、等网络列为任务"暂停中"的原因。但用电池只暂停后台请求，"用户在等"的请求照常全速。
  - 例：用户用电池时手动分拣一封邮件，完全可以跑。GET /tasks 却只能给 mail.triage 一个状态：报"暂停中"，luoke-mail 会把按钮置灰；报"可用"，用户不知道后台整晚没整理。
  - §8 的"需要换代"不在五种状态里。§12 熔断后任务变成什么状态没写（B3 原本写了"相关任务标为不可用"）。
- **理由**：GET /tasks 是配件读状态的唯一入口，枚举一旦发出去就很难改。
- **建议**：
  - 任务状态的"暂停中"只用于整个任务都做不了的情况：撤回待替换、熔断，并在 §12 写明。
  - 用电池、低电量、等内存，改为一个"全机后台运行状态（附原因）"，配合配方里"用电池也做"的任务例外。
  - 等网络并入"下载中"的子原因。
  - "需要换代"加进枚举，或定义为"不支持"的一个子原因。

**10. 允许生成任务"改用专用模型"，但专用模型绕开了派发**
- **位置**：CONTEXT「底座」「专用模型」；DESIGN §5「每档一个底座」、§6「专用模型与后台让路」「功耗与电源」；ADR 0004、0006。
- **问题**：
  - CONTEXT 和 ADR 0004 首句说本档所有生成任务都由底座做，同一段和 §5 又允许"改用专用模型"。
  - 专用模型的请求不经派发；ADR 0006 说主控对它"施加功耗规则"，却没给机制。
  - 例：16 GB 档把 mail.triage 分给一个小专用模型。夜里批量分拣 300 封时，会被当成"用户在交互"，挡住底座上全部后台工作；用电池时也拦不下；它还会和 jiu 的专用模型争 GPU，没有人仲裁。
- **理由**：现有两个配件都没有这样的计划，但留着这条退路，同一条后台请求的行为就会随硬件档变化。
- **建议**：专用模型只用于 jiu 这类非生成、交互打分的任务，删掉 §5 的"或者改用专用模型"；生成任务在某档达不到及格线就标"不支持"。同步修改 CONTEXT、ADR 0004、ADR 0006。

**11. ADR 0005 的分界没贯彻到底：任务参数漏了几类随模型变化的数**
- **位置**：ADR 0005；DESIGN §3「任务参数」、§4「请求里配件能决定的」「输入超长时直接拒绝」、§11 jiu 与 luoke-mail 删除清单；corrector_service.py:54-55，triage.py:314/360，editor.py:68，digest.py:21/210-215。
- **问题**：
  - jiu 的词表奖励 `BONUS_HARD=8.0`、`BONUS_SOFT=2.0` 和 τ 一样，单位是该模型的 nats，§11 却只把 τ 搬进了任务参数。
  - luoke-mail 的输出上限是按条目算的 token 预算（60+30×行数、60+25×人数、60+60×k、1400、900、700），"每行 30 token"取决于分词器。
  - 任务参数里没有输入上限，也没规定单位：配件数不了 token，看不到 §4"超长就拒绝"的阈值。§11 要删的截短重试，原本由内存报错触发；删掉以后，16 GB 档上一份始终放不进内存的长 prompt，按"从不硬挤"会一直等下去。
- **理由**：换底座后评测能发现问题，但修复只能发新版配件、重新验证，这正是 ADR 0005 想避免的。
- **建议**：
  - §11 jiu 把"τ"扩为"τ 和 BONUS_HARD、BONUS_SOFT"。
  - §3 和 §4 规定输出上限由任务参数给出"每条目预算 + 固定开销"，配件只报条目数。
  - GET /tasks 给出按字符计的输入上限，截短逻辑留在配件里，按这个上限截。
  - ADR 0005 Consequences 加一条：配件里任何以 token 或 nats 为单位的常数，一律视为任务参数。

**12. 配件更新时"保留上一版以便回退"不安全**
- **位置**：DESIGN §12「主控重启、自更新与配件更新」、§7、§8 换代（先更新配件）；ADR 0008；research C8；luoke-mail store.py（_migrate_rules、_migrate_old_mail）。
- **问题**：
  - 回退由谁、在什么条件下触发，没有写。
  - 例：换代到底座 B 前，luoke-mail 先升到 0.9。0.9 崩溃后退回 0.8，可 0.8 只在旧底座 A 上验证过，于是机器上跑的是未验证的 0.8 × B。
  - store.py 一启动就做不可逆迁移（例如把 rules 表改名为 rules_v02），旧版本跑在新库上会看不到数据或直接出错。
- **理由**：看起来有保险，实际用不了；而 ADR 0008 验证的是输出质量，覆盖不了"在某个用户的数据上一启动就崩"。
- **建议**：
  - 旧包保留到新版本首次启动、并向主控报告正常（例如连上任务层）为止；只在报告正常之前失败才回退。
  - 配件在迁移前用 `sqlite3` backup 自己做一份快照，回退时由配件恢复。
  - 回退目标必须在当前组合上已验证，否则相关任务暂停。

**13. 撤回清单随配方下发，而用户可以关掉自动更新**
- **位置**：CONTEXT「撤回」；DESIGN §8 更新（"什么时候装"、撤回）。
- **问题**：§8 允许用户关掉自动更新，没把配方区分出来。谨慎的用户关掉之后，实验室因为许可或内核崩溃撤回某个模型，这台机器永远收不到撤回，被撤回的模型一直在跑。
- **理由**：撤回是唯一不经同意的强制手段，送达路径不能被普通的更新开关挡住。
- **建议**：§8 和 CONTEXT「撤回」加一句："拉取配方（至少是撤回清单）不受自动更新开关影响，撤回在拉到时立即生效"；开关只管其余部分的安装。v1 配方随主控一起发（见超前第 5 条）时，同样的规则适用于主控自己的更新检查。

**14. luoke-mail 的现状套不上"app 包、唯一登录项、同一 Team ID"**
- **位置**：DESIGN §8「只有一个登录项」「配件被直接拖进废纸篓」、§10「主控下载的文件」、§11 luoke-mail；luoke-mail desktop.py:32、195-260、324。
- **问题**：
  - luoke-mail 没有 .app，代码是一个靠 PYTHONPATH 指向的 Python 包。开启自动整理时由 LaunchAgent local.luoke-mail 运行 `--service`，否则由启动器按需运行。
  - "螺壳邮件助手.app"是运行时用 osacompile 生成、ad-hoc 签名的启动器。
  - 所以"核对 app 包还在不在""拖进废纸篓就算卸载"对它不成立；ad-hoc 签名和"同一 Team ID 签名并公证"冲突；§11 也没列出 LaunchAgent 和启动器的迁移。
- **理由**：§11 一句"改为通过后台入口"低估了改动，实际要先重新打包。
- **建议**：§11 改为：luoke-mail 打包成签名公证的 .app（包含包代码和预签名的通知 helper），取代 AppleScript 启动器和 LaunchAgent。迁移步骤写上 `launchctl bootout local.luoke-mail` 和删除旧启动器。它由主控启动还是被叫醒，见冗余第 2 条。

**15. "一台机器测各档"忽略了芯片代差异，评测耗时也没有依据**
- **位置**：DESIGN §7「评测」、§13 第 7 项；ADR 0008 正文与 Consequences；research A7、B12。
- **问题**：
  - 同一个模型文件在 M1、M4、M5 上走不同的 Metal 代码路径（oMLX 有针对 M5 NAX 的专门路径），温度为 0 也不保证逐字一致。B12 建议过"芯片代变化时回放子集核对逐条结果"，§7 没采纳。
  - 及格线第 1 层是"硬性条目一条都不能错"，一次数值漂移就可能翻掉一条钓鱼判定。
  - ADR 0008 的耗时估计没有实测依据。
- **理由**：逐版本评测是每次发布的硬关卡，代价估错了，关卡在实践中就会被绕过。
- **建议**：§7 改为"在一台机器上评质量，再在每个芯片代（M1、M4、M5）上回放一个固定子集，核对逐条一致"。先实测一次完整评测的墙钟时间（可以利用 oMLX 的并发批处理），再写 ADR 0008 的代价。

**16. 专用模型引擎的进程归属，以及共用 oMLX Python 的后果，都没写清**
- **位置**：DESIGN §2、§5「引擎」「配件运行时」、§10（同一 Team ID）、§12；CONTEXT「引擎」；ADR 0001、0006；research A2；run_eval.py:31-34；oMLX _build_info.py。
- **问题**：
  - §2、§5、ADR 0001 写"进程内的 mlx-lm"，§12 写"引擎是独立受监管的进程"。A2 原意是"在主控监管的子进程里以库方式调用"，DESIGN 丢了"子进程"三个字；实现者如果把它放进主控进程，主控每次自更新都会让 jiu 断掉。
  - jiu 今天已经在用 oMLX 自带的 cpython-3.11 和 mlx（mlx 0.32.2、mlx-lm 开发版提交 94cdcae）。共用就意味着每次升级 oMLX，jiu 的证据都要重测。
  - oMLX 由上游的 Team ID 签名；build 号里的 macos26-27 说明它可能按 macOS 版本分别出包。
- **理由**：这几点决定主控的进程结构、安装包大小、签名范围，以及升级引擎时哪些证据要重测。
- **建议**：
  - §2、§5、ADR 0001 统一写成"主控监管的 mlx-lm 工作进程（以库方式调用）"。
  - 如果共用 oMLX 的 Python，配方里规定专用模型的引擎版本跟随 oMLX，升级时回放 jiu 的评测集。
  - §10 二选一：用实验室的 Developer ID 重签并公证现有二进制；或为引擎包设上游 Team ID 白名单。
  - 配方里的引擎版本必要时带上 macOS 这一维。

**17. 关键路径上依赖的几项 macOS 行为还没核实**
- **位置**：DESIGN §8「只有一个登录项」、§9、§10「主控下载的文件」、§12「主控重启」；CONTEXT「主控安装包」；ime_eval main.swift:228-248、874-888。
- **问题**：
  - 权限归属：主控用 Process 或 posix_spawn 拉起 jiu 时，辅助功能和输入监控权限会算在主控头上，用户会看到"螺壳主控想监听键盘"。只有经 LaunchServices 启动，权限才归 jiu。
  - quarantine：从带 quarantine 标记的 DMG 拷出的 .app，即使已公证，首次启动也会弹"来自互联网"的确认框，和 §9"不能弹抢焦点的窗口"冲突。安装器在 DMG 里运行时会被 App Translocation，SMAppService 注册可能指向一个随机路径。
  - "引擎活过主控重启"是否会随主控退出被连带结束，需要实测。
- **理由**：这些都在"装上就能用"的路径上，做错的后果正好打在精品体验上。
- **建议**：
  - §8 写明配件一律经 `NSWorkspace.openApplication` 启动。
  - §10 补上"安装器移除 quarantine、检测 translocation"。
  - §12 推荐 v1 接受"主控重启即引擎重启"：专用模型只有 0.43 GB，重载很快；底座重载放在安静时刻。
  - 以上全部列入 §13 的实测项。

**18. 实验室自己开发和评测的回路没有定义（缺口）**
- **位置**：ADR 0003（不设开发者模式）、ADR 0008；DESIGN §7、§3「签名与版本」；research A7。
- **问题**：负责人改一句提示词，要先经主控跑起来才能调试和评测。可主控只认签名配方里的已验证版本，又没有开发者模式。结果只剩两条路：
  - 绕开主控直连引擎：参数覆盖、特殊 token 中和都没被测到，证据失真；
  - 在正式构建里加隐藏开关：违反 ADR 0003。
- **理由**：开工第一天就会碰到。ADR 0003 允许"自己改代码"，所以这是缺口，不是矛盾。
- **建议**：在 ADR 0003 Consequences 里定义"实验室构建"：
  - 用不同的 bundle id，独立的主控环境目录和 socket 路径，避免和开发机上的正式主控抢同一个 socket；
  - 内置一把实验室测试公钥来加载本地配方，不要做成"关掉验签"；
  - 可以接受未验证的配件版本；
  - 正式构建不编译这些代码路径。
  - CONTEXT 增加术语"实验室构建"。

### 低

**19. 主控到引擎这一跳缺两个加固点**
- **位置**：ADR 0007；DESIGN §10「本机边界·引擎」、§12「主控重启」；oMLX settings.py:1564-1570；luoke-mail server.py:1058-1064。
- **问题**：ADR 0007"socket 从结构上消除风险"的论证限定在任务层，本身不矛盾。但引擎这一跳缺两点：
  - 没写"确认监听端口的是自己拉起的子进程之前，不发请求和密钥"；
  - oMLX 不保存命令行传入的 api key。§12 要求主控重启后重连仍在运行的引擎，主控就得自己保存这把密钥。
- **理由**：端口抢占的窗口很窄，但请求里是完整的邮件正文。
- **建议**：§10 补"按 PID 核对监听者"；§12 写明密钥存在 0700 目录（如果采纳第 17 条"主控重启即引擎重启"，就不需要）。luoke-mail 网页现有的 token + Host 校验，写进配件接入要求。

**20. 任务层的调度字段和"不能立即执行"的含义没列清**
- **位置**：DESIGN §4「请求里配件能决定的」「同步与异步」、§6；CONTEXT「请求等级」「预热」；research A8。
- **问题**：
  - §4 的"只有消息、格式、长度"指的是影响推理结果的字段，本身不矛盾。但请求等级、本次允许用电池、仍要加载、预热、取消在请求里怎么表示，还没有列。
  - "不能立即执行就马上返回原因码"应只指需要用户做决定、暂停中、不支持这几种情况。冷加载这类正常等待没有"加载中"信号，而 luoke-mail 有 300 s 读超时。
- **理由**：这是任务层协议的第一批字段，写代码前就该定下来。
- **建议**：
  - §4 拆成"推理字段白名单"和"调度字段清单"（放 header 或单独端点），CONTEXT「请求等级」注明它在请求里怎么表示。
  - 写明"不能立即执行"的范围，并为排队、加载中提供进度事件。
  - §6 内存那条改为"主控返回原因码和占用者名单，由配件在当前界面给出选项"，和 §9 对齐。

**21. 任务属性的来源和参数归属，措辞不清**
- **位置**：CONTEXT「主要任务」「任务参数」；DESIGN §3「任务参数」「证据的记录格式」、§4「任务」、§8 安装流程第 1 步；ADR 0001、0005。
- **问题**：
  - "主要任务"写成"配件登记时标明"，可 §8 要在配件装上之前预检主要任务的状态，§3 的配方内容里又没有这个标记。
  - 实验室在某档做不到思考时怎么办，没有写。
  - "底座参数"在 ADR 0001 和 §3 都在用，CONTEXT 却没有这个条目。
- **理由**：写配方格式时，这些字段不知道该放在哪里。
- **建议**：
  - 主要/可选标记放进配方（或配件包清单），安装器在安装前从那里读。
  - 规定"某档做不到思考就标为不支持，不悄悄改成不思考"。
  - CONTEXT 单列"底座参数"（或叫"加载参数"），并写明归属：思考意图在任务定义里，各档的取值在任务参数里，到模板参数的映射在适配器或底座参数里。

**22. 换代切换在小内存档上的顺序没写**
- **位置**：DESIGN §8「换代·切换」；CONTEXT「冒烟检查」；ADR 0004；research B2。
- **问题**：16 GB 档上，对新底座的冒烟检查必须等旧底座卸载以后才能做。B2 原有"冒烟检查按后台等级排队"，写进 DESIGN 时丢了。ADR 0004 提到的"卸载后立即加载的竞态"，在换代时同样会遇到。
- **理由**：16 GB 档是实验室有实机、也最容易出问题的一档。
- **建议**：§8 写明：冒烟检查作为后台任务，在旧底座空闲卸载后进行；当前的后台请求跑完再切换，期间新请求排队。"卸载后等内存回收确认再加载"列入 §12。换代本身建议推迟，见超前第 2 条。

## 二、冗余

**1. 后台入口和"主控启动常驻配件"是两套机制，v1 只需要一套（高，需负责人确认）**
- **位置**：CONTEXT「后台入口」；DESIGN §1、§2、§6「其他情况」、§8「只有一个登录项」、§11 luoke-mail；luoke-mail desktop.py、background.py、server.py（set_auto）。
- **问题**：
  - jiu 是常驻的菜单栏程序。luoke-mail 开启自动整理后，就是登录时启动、常驻运行，由 AutoSync 每 30 s 检查一次，有空闲工作时每 5 s 一次。这种循环适合常驻，不适合定时叫醒。
  - 后台入口要定义计划格式、错过的计划怎么补、叫醒时的电源规则、做完怎么退出，还要处理被叫醒的进程和界面服务争同一把锁（InstanceLock）。
  - 不过 §11 是负责人有意把 luoke-mail 改成"按计划叫醒"（来源 A10），所以这是一个取舍：保持常驻改动最小；按需拉起加定时叫醒能省一个常驻 Python 进程，代价是重构 luoke-mail 的服务模型、新增一套叫醒协议。
- **理由**：两条路径并存，会出现"同一个配件既常驻又被叫醒"的边界情况；电源规则已经在派发处统一执行。
- **建议**：
  - v1 选常驻：主控维护一份"登录时启动"列表（jiu，以及开启了自动整理的 luoke-mail），配件意外退出就重启。
  - luoke-mail 删掉自己的 LaunchAgent，保留 AutoSync，只把模型调用改发到任务层，并遵守主控返回的原因码。
  - §8 改为"v1 的配件都由主控启动并常驻"；§11 那句改为"后台请求标'后台'等级"。
  - 后台入口和 §6"叫醒时同样遵守"标为以后。

**2. "用户是否在交互"有三套判定**
- **位置**：CONTEXT「安静时刻」「预热」；DESIGN §5「驻留」、§6「专用模型与后台让路」、§8「什么时候装」「换代·切换」、§13 第 6 项；ADR 0006；research A9。
- **问题**：
  - 三套判定：CONTEXT 的安静时刻是"没有'用户在等'的请求，且配件空闲几分钟"；§8 换代切换只看此刻有没有"用户在等"的请求；§6 是"专用模型最近几秒有请求"，不看请求等级。
  - jiu 每次停手 0.35 s 打一次分。按 §8，两次打分之间的空隙就可以开始切换底座、加载几十 GB，直接打在 jiu 的延迟上。
  - 还有几处措辞问题：§5 的"活跃"没定义；§13.6 用了 CONTEXT 列为避免用词的"保温"；功耗档的"安静"和"安静时刻"撞词。
- **理由**：派发、更新、换代各自定义"空闲"，实现时会写出几套计时器，行为互相打架。
- **建议**：
  - CONTEXT 只定义两个谓词："交互中"（任一路径最近 N 秒有"用户在等"的请求，或有配件发起了预热）和"安静时刻"（连续 M 分钟不处于交互中）。
  - 专用模型的请求也带请求等级（恢复 research A9 的建议）。
  - §6、§8 的切换和冒烟、§8 和 §12 的自动安装，统一引用这两个词。
  - §5 改为"配件运行期间常驻"；§13.6 去掉"保温"；功耗档的第三档改名，例如"轻柔"。

**3. 配件令牌不提供安全性，和请求里的任务名、自报 id 重复**
- **位置**：CONTEXT「配件令牌」「任务层」；DESIGN §1、§2、§4「通道」「模型层」、§10「本机边界·任务层」；ADR 0007。
- **问题**：
  - 文档自己说令牌"不是安全措施"。socket 在 0700 目录里，本账户的进程都能读到令牌文件；Python 配件共用运行时，看对端签名也分不出是哪个配件。
  - 令牌却要安装器签发、配件保存、主控维护、重装时重发，开发构建还会因此连不上。
  - 另一方面，本账户任何进程都能把任务层当成通用推理入口来用；以后收紧时会伤到这些调用方，正是 §4 担心的"先开放再收回"。
- **理由**：识别配件需要的信息已经在路径的任务名里，令牌只多出几个故障点。
- **建议**：
  - v1 删去令牌，配件在请求头里自报 id 和版本（例如 `X-Luoke-Accessory`），主控按配方任务表校验任务归属。注意按编号查询或取消、预热、打分这些端点也要带上配件名或任务名。
  - ADR 0007 或 §10 写明"未登记的调用方不受支持，以后可能失效"。
  - CONTEXT 的「配件令牌」改为「配件标识」。

**4. 同一条规则在 CONTEXT、DESIGN、ADR 各写一遍，已经对不上**
- **位置**：CLAUDE.md「约定」；CONTEXT 多条；DESIGN §3–§10；ADR 0001、0005、0007、0008。
- **问题**：已经出现的不一致：
  - oMLX 锁定方式在三处重复，其中"关闭 prompt 日志"没有对应参数；
  - 维持期 CONTEXT 写"暂定 6 个月"，§8 写成定数；
  - "需要换代"不在状态枚举里；
  - CONTEXT 把"现行版本"列为避免用词，§7 和 ADR 0008 仍在用；"现役组合""现役底座"都没定义；
  - 证据的键和 §3 记录格式的字段对不上；
  - CONTEXT 里写了规则，违反 CLAUDE.md 的约定。
- **理由**：设计还在快速变动，每改一处都要同步三处；读者（包括 AI 代理）不知道以哪一处为准。
- **建议**：
  - 立一条单一来源规则：DESIGN 是现行规则的唯一准绳；CONTEXT 只写一两句定义，不写数字和规则；ADR 保持决定当时的记录，冲突时以 DESIGN 为准，需要改正文时追加 superseded 说明。
  - 先清理：§10 的 oMLX 参数改为"见 §5"；删掉"现行版本"；定义"现役组合"；统一证据的键。

**5. 配方下发了完整证据和逐条结果**
- **位置**：CONTEXT「配方」「证据」「依据」；DESIGN §3「内容」「证据的记录格式」、§9；ADR 0008；research B12。
- **问题**：
  - "已验证版本"是实验室签名的发布判定，和证据是"结论 + 依据"的关系，不算冗余。
  - 但 §3 把含逐条结果的完整证据放进了随主控下发的配方。按 ADR 0008，每发一个配件版本就多出"底座数 × 任务数"份结果，下发到每台机器上。
  - "不支持"的原因也在任务状态和依据里各存一份。
- **理由**：配方体积和出现不一致的风险，都会随版本数增长。
- **建议**：配方里每个（配件版本 × 硬件档）只下发一条：是否已验证、依据文案、芯片/日期/速度摘要、证据哈希。逐条结果留在实验室仓库，用哈希引用。"不支持"的原因只以依据文案为来源。

**6. 电池的一次性许可可以简化，电池开关要和功耗档放在一起**
- **位置**：CONTEXT「功耗档」；DESIGN §6「功耗与电源」、§9、§11；ADR 0002；luoke-mail engines.py（POWER 0/1/3）。
- **问题**：
  - 功耗档、电池开关、单次许可、配方标记、低电量模式、过热是正交的几个维度，不算重复；三档功耗也是从 luoke-mail 迁移来的现有功能，不是超前。
  - 真正的问题有两个：用电池时功耗档对后台没有可见效果，用户会以为"全速"失灵了；一次性许可需要主控跟踪"插上电源或做完就失效"的状态，而它其实等价于配件不再给请求设这个字段。
- **理由**：给普通用户的开关要能一眼看懂，主控里也少维护一份状态。
- **建议**：
  - 一次性许可改为请求字段 `allow_battery`，只用于用户亲手启动的工作，删掉主控侧的许可状态。
  - 配方的"用电池也做"保留为一个布尔任务参数（耗电随档变化，配件不知道底座是谁），v1 可以先不填。
  - 设置里把"用电池时：暂停后台（默认）/也运行"和功耗档并列显示。
  - 过热用 `ProcessInfo.thermalState`，serious 及以上就暂停后台。

**7. "模型层"在 v1 没有使用者**
- **位置**：CONTEXT「模型层」「共享模型」；DESIGN §4「模型层」、§5「每档一个底座」最后一句、§12「内存压力」；ADR 0006。
- **问题**：
  - 模型层只读、不能推理；配件不点名模型；答复的 `model` 字段已经给出实际用的底座。它唯一的使用者，是 §1 已推迟的"对其他 OpenAI 兼容工具开放"。
  - "共享模型"是 ADR 0006 两条路径中的一方，v1 只有底座一个实例，但这个类别不多余，保留即可。
- **理由**：多一个术语，就多一个"它和 X 有什么区别"的问题。
- **建议**：模型层从 CONTEXT 和 §4 移到 §1 的推迟事项，和"对其他工具开放"合在一起；§5 关于嵌入、语音识别小模型的那句也移过去；§12 的 warn 级改写为"底座空闲就卸载"。

## 三、过于超前

**1. 全文没有分期（高）**
- **位置**：DESIGN 全文（§5、§6、§11 用了"第一版"，但 §8 的换代、维持期、撤回，§8 和 §11 的后台入口，§10 的社区测试者都没标）；§12 的 7 组 23 条；§13。
- **问题**：v0 按"大量陌生用户、多个配件、长期运营"一次画全。AI 代理照文档实现，会把所有内容都当成 v1 的范围。实际是一个人、两个自家配件、三台机器，没有外部用户。
- **理由**：两个配件都由实验室出，可以和主控、配方作为一列"发布车"同步发版。跨版本兼容、维持期、独立配方通道，都是为"各方独立发版、用户机器上版本参差"设计的，v1 里没有这个问题。
- **建议**：
  - 给负责人提一个"§0 分期"提案，把每条规则标为 v1 / v1.x / 以后（见第四节）。这是产品决定，由负责人拍板，不直接写进文档。
  - §13 按关键路径重排：
    0. jiu 经主控的延迟实测（矛盾第 5 条）；
    1. 实验室量化 v1 要用的 2–3 个模型并重测，只查这几个模型的许可；
    2. 任务层和最小派发；
    3. 接入 luoke-mail 和 jiu；
    4. 引擎重签和公证。
  - v1 必须一次做对、以后改很贵的几项：jiu 的 bundle id、Team ID、`~/Applications/纠.app` 路径（改了就丢辅助功能授权）；主控环境路径（和 `~/.luoke` 分开）；socket 路径；主控的 bundle id 和登录项机制；配方里的版本号、签名、`min_hub_version`、`revoked` 字段。

**2. 换代整套生命周期，在第一次换代之前一次也走不到（高）**
- **位置**：DESIGN §8「换代」「维持期」「撤回」、§5「省内存模式」「引擎版本属于配方」、§12「引擎故障」「系统更新与换机」、§3「内容」；CONTEXT 生命周期一节；ADR 0004、0008；research A5、A12、B7。
- **问题**：
  - v1 首发时每档装的就是第一个底座。"旧底座保留 14 天""维持期到期""拒绝换代后双底座验证"这些路径，头几个月一次也走不到，却都要写、要测、要在三台机器上验证。
  - 这是主控里最复杂的状态机：两个底座 × 同意/拒绝/推迟 × 撤回 × 熔断。维持期还会让每次发配件的评测量翻倍。
- **理由**：推迟的代价很小，换代机制可以随以后某个主控版本下发。前提是配方能声明 `min_hub_version`，A5 提过，但 §3 没写。
- **建议**：
  - v1 不做换代、维持期、省内存模式。配方加 `min_hub_version`，并预留"需要换代"状态和 `revoked` 字段。
  - v1 保留一个最小子集：
    - 引擎包随主控下发，保留上一版，冒烟检查失败就退回；
    - 熔断本身，即把相关任务标为不可用；
    - 用迁移助理换到内存不同的 Mac 时，提示需要下载本档底座，征得同意后删掉不适用的旧底座（B7，§12 没写）；
    - 撤回靠主控的自动更新（Sparkle 一类）加社区公告。
  - 维持期留还是删、定多长，由负责人按当时的用户规模决定；也可以只承诺"已装版本照常能用、不再收新版本"，免掉双底座验证。

**3. 后台请求的异步作业协议和多配件仲裁过重（高）**
- **位置**：DESIGN §4「同步与异步」、§5「驻留」、§6「请求等级与打断」、§11；CONTEXT「打断」「预热」；ADR 0004、0006；research A8、interrupt-and-resume §2。
- **问题**：
  - v1 用底座的只有 luoke-mail，"按配件轮流"永远不会触发。
  - 编号、查询、取消、主控内存队列、主控重启码、保留部分文字（只对已推迟的续写有用），要求 luoke-mail 把同步调用改成提交加轮询。
  - A8 的真实动机有两个：300 s 读超时会把"用电池暂停"报成超时；Python 取消不了进行中的请求。用"不能跑就立即返回原因码"加"关闭 socket 即取消"就能解决。
- **理由**：这是 v1 关键路径上最贵的一块，而两个配件随发布车一起发，协议以后随时可以改。
- **建议**：
  - v1 后台请求走同步调用，能马上跑才接下，否则立即返回原因码和 `retry_after`；被打断时返回 `interrupted`，由 AutoSync 重试。
  - 主控到 oMLX 仍用流式（oMLX 只在连接断开时中止），但不保留部分文字。
  - 打断前做一行粗估：剩余 prefill ÷ 速度 + 剩余 token ÷ 速度，和打断延迟（约 2 s 轮询加一个 prefill 块）比，剩余更短就让它跑完。两条核实意见对要不要估算有分歧，这里取成本最低的做法。
  - 预热只做"luoke-mail 界面打开期间不卸载底座"。
  - 主控队列和按配件轮流放到 v1.x；复杂的代价模型和断点续做放到以后。

**4. 评测门槛按成熟期设计（高）**
- **位置**：ADR 0008；DESIGN §7「及格线」「发布前必须验证」、§3「签名与版本」、§13 第 1、2 项；research A7、C9。
- **问题**：
  - 首发不需要第 3 层非劣检验，但之后 luoke-mail 每改一句提示词都会触发它，而 40 封邮件分不清是真变差还是随机波动（A7 估计每个任务要约 200 条）。
  - 能跑大底座的只有负责人日常用的 M5 Max，自动触发的 CI 会在他工作时加载几十 GB 的模型。
  - "离线保管的密钥"意味着每发一个版本，负责人都要亲手签一次。
- **理由**：发布前跑评测是封闭配方的落脚点，应该保留；贵的是小样本下站不住的统计检验，以及 CI 基础设施和人工签名。
- **建议**：
  - v1 由负责人手动跑发布脚本，自动判定第 1 层（硬性条目全过、输出格式合法）和第 2 层（总分不低于底线）。
  - 第 3 层暂时改为"硬性条目零回退，且总分不低于上一个已验证版本减去容差"，并输出逐条差异报告，负责人看过再放行。
  - 私钥不要放成普通文件：这台机器上跑着能读负责人目录的 AI 代理，而主控是整个家族的单点（C9）。用 Secure Enclave（CryptoKit 加 Touch ID，只支持 P-256）或硬件密钥，签名和放行合成一次指纹确认。
  - 评测集扩到约 200 条后，在 v1.x 启用正式的非劣检验；CI 自动化放到以后。

**5. 配方的独立更新通道和离线签名**
- **位置**：DESIGN §3「签名与版本」「独立更新」、§10；ADR 0003；research A4、A5。
- **问题**：
  - 独立通道要准备密钥保管、签名工具、托管、拉取、验签、防回滚，它的价值是"换底座不用发新版主控"，发布车用不上。配方打进 .app 后，已经受到代码签名和公证保护。
  - 配方随主控一起发时，"拒收比本地旧的配方"等于禁止用户手动装回旧版主控。
- **理由**：只要 v1 的配方格式留好版本号和签名字段，以后再加签名不会破坏任何东西。
- **建议**：v1 的配方放在 .app 的 `Contents/Resources` 里，直接从包内读取；只记录版本号，不拒收旧配方；模型照样按哈希校验。独立通道、签名（用第 4 条的方案）和防回滚放到 v1.x。

**6. 硬件档的数量应该和能实测的机器对齐**
- **位置**：DESIGN §5「分档」「省内存模式」「驻留」、§7「用户机器上」、§13 第 7 项；ADR 0004；research A1。
- **问题**：
  - 设计没定档数，"约 4 档"只是 A1 的建议，所以这一条是待办 7 的输入，不是对现设计的修改。
  - 实验室只覆盖 16 GB 和 128 GB。每多一档，就多一个底座要选、要量化、要托管、要证明装得下、要补速度证据。
  - 反过来，把中间档一律压到 16 GB 档，会让 24–64 GB 的 Pro 机型用 16 GB 级别的底座，和"精品"的目标相悖。
- **理由**："实验室验证"的承诺需要证据兜底，同时不能牺牲主流 Pro 机型的体验。
- **建议**：
  - v1 配方只收经过实机或"公式 + M5 Max 限内存实测"确认装得下的档，可以考虑三档；中间档的速度靠本机冒烟检查和"较慢"状态兜底；没测过的芯片，依据里不写速度。
  - 8 GB 的 Mac 只开 jiu。
  - 空闲卸载时长先用一个全局默认值。
  - 省内存模式的"主动建议"放到以后。

**7. 双站同名发布，且各类包的托管位置没写**
- **位置**：DESIGN §3「模型来源」、§8、§10；ADR 0003 Consequences；research A4。
- **问题**：
  - 每个模型要在 Hugging Face 和 ModelScope 各传一份，每次修正都要两边同步；两边一旦不一致，会出现"只有部分用户哈希对不上"的难查故障。
  - 设计没写主控包、配件包、引擎包和配方放在哪里。它们同样有国内能否访问的问题，A4 还提到要先确认能否做 ICP 备案。
- **理由**：双站同步是持续的人工成本，而以后加镜像只是多填一个 URL。
- **建议**：配方里每个文件的下载源写成 URL 列表、以哈希为准。v1 只填一个主通道：以国内用户为主就选 ModelScope，海外也能访问。补上各类包的托管位置；第二个站点放到 v1.x。

**8. "配件运行时"作为主控管理的共享 Python**
- **位置**：DESIGN §5「配件运行时」「引擎」、§3「证据的记录格式」；CONTEXT「配件运行时」「证据」；ADR 0001；research A2。
- **问题**：
  - 主控环境里可能同时有三份 Python：oMLX 自带的、跑专用模型的、实验室签名的配件运行时。
  - 共享运行时是一个要单独签名、分发、更新的组件；升级它会改变所有 Python 配件的行为（例如 luoke-mail 的邮件解析），而证据的键里没有运行时版本。
- **理由**：共享省下的是几份解释器的磁盘空间，代价是多一个要验证的组件。
- **建议**：先按矛盾第 6 条定下 jiu 是否保留 Python。然后推荐每个 Python 配件自带一份 python-build-standalone，随自己的 .app 一起签名和更新，这样运行时版本自然跟着配件版本走。不推荐绑在 oMLX 的 Python 上，那样引擎一升级，luoke-mail 的运行环境也跟着变。共享运行时放到以后。

**9. 统一安装包，以及主控兼任全家族的安装器和更新器（需负责人确认）**
- **位置**：DESIGN §2、§8「安装·只有一个安装包」「更新」、§12；CONTEXT「主控安装包」；ADR 0002。
- **问题**：
  - 这套流程要识别来源配件、换名字和图标、做预检、合并同意、失败时连主控一起撤掉，还要管理四类包的更新。它依赖的真实下载路径和失败率，现在还没有数据。
  - .app 的目录名不在签名范围内，同一个签好名的安装器放进不同的 DMG 就能显示不同名字，只有换图标才需要另出构建。DMG 里的旁路配置文件，会因为 App Translocation 读不到。
- **理由**：ADR 0002 的核心是让用户对资源占用知情同意，首次运行时的预检和一屏同意就能做到。但"先装主控"正是 ADR 0002 否决过的路径，需要负责人确认。
- **建议**：
  - v1：主控发一个公证过的 DMG；jiu 发公证过的 .app；主控首次运行时做预检、一屏同意、下载模型；安装器按自己 bundle 的文件名预选配件，图标统一。
  - 主控自更新用 Sparkle（它会带来第二把 EdDSA 密钥，要和配方密钥一起管理）。
  - 配件和引擎随发布车更新。
  - 主控代管配件更新、逐配件的品牌化放到 v1.x。

**10. 复用用户环境里的模型文件，几乎不会命中**
- **位置**：CONTEXT「复用」「用户环境」；DESIGN §2、§10「本机边界·用户环境」、§12「复用」；ADR 0003；research C11、B10。
- **问题**：
  - ADR 0003 只收实验室自己量化、按哈希认定的文件。用户机器上现有的模型是社区量化或自己转换的，哈希对不上；Ollama 的 GGUF 文件更不可能。
  - 为了这条几乎走不到的路径，要做目录白名单扫描、全量哈希、APFS clone、跨卷征求同意，还多出一项"读取用户目录"的隐私承诺。
- **理由**：眼下唯一现实的命中是负责人自己的机器，手动拷贝就能解决。
- **建议**：
  - 复用移到 §1 的推迟事项，等实验室仓库有了外部下载量再评估。
  - 删掉 §12「复用」和 §10 读取模型文件夹的白名单；用户环境只保留"观察内存占用"（看进程即可）。"不读用户引擎的设置文件"作为禁止性规则保留。
  - CONTEXT 的「复用」注明它和 ADR 0003 的关系。

**11. 社区测试者自动上报**
- **位置**：CONTEXT「诊断信息」「社区测试者」；DESIGN §10「不回传数据」、§13 第 7 项；research A13。
- **问题**：自动上报需要一个接收端，还要定上报格式、开关界面、数据保留策略和隐私说明。现在没有外部用户，待办 7 却靠它来补齐档位数据。
- **理由**：在有足够用户之前它产生不了数据，却要先搭一个需要长期维护的服务端。
- **建议**：
  - v1 只做"导出诊断信息"，内容补上机型、芯片、内存和冒烟实测速度，由测试者在社区里自愿提交。
  - 也可以先给社区发一个独立的测速脚本，在用户自己的 oMLX 上跑候选底座。
  - 自动上报放到以后，CONTEXT 里的术语保留，注明 v1 没有实现。

**12. §8 卸载回收和 §12 实现事项没有分期**
- **位置**：DESIGN §8「卸载与回收」、§6「观察用户环境」、§12 全部、§11 luoke-mem；luoke-mail credstore.py。
- **问题**：
  - 一部分条目依赖已推迟的功能（熔断"作为换代后回退的依据"、主控代管配件更新、自更新前排空），另一部分在 v1 便宜而且重要。
  - 数据删除有个真缺口：§11 说 `~/.luoke/mem.db` 随 luoke-mail 发布但不归主控管，钥匙串里还有邮箱密码；而 §8 规定"每个配件只删自己的数据"，这两样算不算 luoke-mail 的数据没有定义。
- **理由**：不分期，v1 的范围会悄悄膨胀；依赖推迟功能的条目单独实现出来也用不上。
- **建议**：
  - v1 保留：下载的全部条目；崩溃后重试一次、看门狗、熔断本身；内存压力的 warn 和 critical 两级（16 GB 档上 critical 并不罕见）；睡眠与时钟；系统升级后补做冒烟检查；tmutil 排除；检测登录项被关；按引用回收的核心部分（存储页加卸载时询问）。
  - v1.x：每日核对、磁盘紧张提醒、迁移助理实测。
  - 以后：多账户内存归因。
  - 先定下 mem.db 和凭据的归属；用户直接把配件拖进废纸篓时，主控至少提示"数据还在、放在哪里"。
