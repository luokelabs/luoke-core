# luoke-core 设计

- **版本**：v0.1（2026-10-09），设计阶段，还没有代码。
- **来源**：v0（commit `5116ded`）是 2026-10-08 至 10-09 与负责人逐条拷问定下的 51 个决定。v0.1 按一轮设计审查（[docs/research/design-review-v0.md](research/design-review-v0.md)）和两轮核对修正矛盾、去掉冗余、做了分期；2026-10-09 授权"应该做的都做"。相对 v0 改动了的地方列在 §0.3，负责人可以否决其中任何一条。
- **不针对具体配件**：主控的设计只写通用机制。现有配件（luoke-mail、螺壳输入法）只是需求来源；它们的具体数值写进配方，接入改动在配件自己的仓库里做，需求来源和接入要点见 [docs/research/accessory-requirements.md](research/accessory-requirements.md)。
- **准绳**：本文是现行规则的唯一准绳。[CONTEXT.md](../CONTEXT.md) 只给术语的定义，不写规则和数字；[docs/adr/](adr/) 是做决定当时的记录，后来的修订以文末"修订"段落追加，与本文冲突时以本文为准；[docs/research/](research/) 是参考，不是结论。

## 0. 分期

> v1 的实际开工范围以 [docs/V1.md](V1.md) 为准。它在 §0.2 的 v1 列上又砍了一刀：整套更新机制、按配件命名的 DMG、按引用回收等推到"正式发布前必做"（V1.md §11）。本节保留的是长期分期。

### 0.1 v1 的目标

v1 让负责人和少数社区测试者在自己的 Mac 上，通过主控用上现有的三个配件（luoke-mail、螺壳输入法，以及作为组件配件的 luoke-mem），并验证三件事：任务层和派发能不能撑起不止一个配件；16 GB 档上交互式的打分任务和后台批量任务能不能共存；实验室评测和发布的流程走不走得通。

v1 按**发布车**发布（ADR 0009）：一次发布由一个发布版本号标识，配方里的发布清单记录这次发布包含哪些配件版本和引擎包版本，它们一起评测、一起发布。配件和引擎包各自保留自己的版本号；引擎包版本在 oMLX、它的 Python、mlx、mlx-lm 或启动清单任一变化时都要变。各方独立发版时才需要的机制（配方独立通道、跨版本兼容）放到 v1.x。v1 期间各硬件档的模型文件不变；唯一的例外是底座或专用模型被撤回后的替换（§8）。

### 0.3 相对 v0 的改动

括号里是 v0（commit `5116ded`）中对应的位置。负责人可以否决任何一条。

**模型与引擎**
1. **专用模型只用于打分任务**（v0 §5「每档一个底座」允许生成任务"改用专用模型"）。专用模型的请求不经派发，拿它跑批量生成会把夜里批量处理几百条也当成"交互中"；生成任务在底座上不达标就标"不支持"。同时删去"嵌入、语音识别这类小模型可以在预算内另外常驻"，推到以后（§1）。
2. **专用模型跑在主控监管的 mlx-lm 工作进程里，用引擎包里的 Python；升级引擎包也要回放只用专用模型的配件的评测集**（v0 §5"专用模型用进程内的 mlx-lm"；v0 没有规定专用模型用哪份 Python）。
3. **v1 主控重启即重启引擎**（v0 §12"只要引擎版本没变，主控重启时不卸载模型"）。引擎会不会随主控退出被连带结束还没实测；代价是每次主控自更新，用专用模型的配件会停一下，所以自更新只在安静时刻，后台请求返回 `interrupted` 而不是排空（v0 §12"先排空请求"）。
4. **oMLX 的启动清单改写**（v0 §5「怎么用 oMLX」、§10"关闭 prompt 日志"）：初稿关于 SSD 缓存默认关闭的说法是错的（见 ADR 0001 修订）；现在用 `--no-cache` 或只放内存的热缓存（实测再定）、`--no-hf-cache`、`--memory-guard-gb`、固定日志级别；oMLX 没有关闭 prompt 日志的开关，改为固定日志级别加标记字符串测试，测试不过的引擎包版本不进配方。
5. **oMLX 内存保护的拒绝、驱逐和全部中止一般按"内存不够"处理，不计入熔断**（v0 §12「引擎故障」把它们算作故障）。环境里内存紧张不是引擎缺陷，旧版引擎照样会中止。
6. **"仍然加载（可能会卡）"推到以后**（v0 §6「内存·从不硬挤」）。v1 里 oMLX 自带的内存保护会直接拒绝超出天花板的加载；以后要做，就换更高的天花板重启引擎，会打断正在跑的请求。
7. **内存压力到 critical 级、卸载底座后仍不够时，专用模型也会卸载**（v0 §5 专用模型"在配件活跃期间一直常驻"、§12 critical 级只卸载底座）；**压力恢复后**改为持续几分钟、确认内存回收再加载（v0 §12 用 FULL_FIRST/FULL_MAX 退避）。

**配方、评测与质量**
8. **证据、任务参数和已验证版本按"组合"（一个模型文件 + 一个引擎包版本）记录**（v0 §3 任务参数按"任务 × 硬件档"、§4"一个任务只有一套任务参数、一份证据"、§7"在所有现役底座上过评测"；v0 CONTEXT「证据」已按"配件版本 × 模型文件 × 引擎版本 × 硬件档"记录，与 §4 矛盾）。现在证据去掉了硬件档这一维，只有与内存有关的任务参数按硬件档细分。这样同一档的新旧底座、只用专用模型的配件、只升级引擎这三种情况都放得下。
9. **派发不再决定用哪个模型**（v0 CONTEXT「派发」"决定交给哪个模型"），改由这台 Mac 的模型分配决定；**答复的 `model` 字段改写组合**（v0 §4"写实际用的底座"）。
10. **配方不再下发完整证据和及格线，只带依据摘要和证据哈希**（v0 §3「内容」"证据和及格线"、CONTEXT v0「证据」"写在配方里"）。逐条结果和及格线留在实验室。
11. **速度只用本机实测**（v0 §7 要求速度在几台有代表性的芯片上测、写进证据；§9 依据显示实验室芯片上的速度；§12 看门狗按证据里的速度设超时）。实验室只在任务写明的机器上测声明了延迟要求的任务（§7）；依据只写质量结论；看门狗按本机实测设超时，第一次冒烟检查之前用配方给的保守默认值。
12. **延迟不进及格线，改为单独的"延迟要求"**（v0 §11 把一个配件的延迟写进了及格线；v0 §7 的延迟要求只在用户机器上提示）。
13. **没有评测集的任务不能以"可选任务"上线**（v0 §11"还没有判分规则的任务，先标为可选任务"）。主要和可选只表示重要程度，不豁免评测。
14. **每代芯片子集回放核对，作为发布关卡**（v0 §7 只说质量可以在一台机器上测各档）。不同芯片走不同的 Metal 代码路径。
15. **新任务随发布车上线**（v0 §3"评测 → 写进配方 → 发配件"）：先评测，写进这次发布的配方，再和配件同车发布；v1.x 独立发版后恢复原来的顺序。
16. **配方签名的私钥从"离线保管"改为放在硬件密钥或 Secure Enclave 里**（v0 §3「签名与版本」）。这台机器上跑着能读负责人目录的 AI 代理，私钥不能是普通文件；签名和放行合成发布脚本里的一次指纹确认。
17. **新增"实验室构建"**（是 v0 §7"主控只安装已验证的版本"和 ADR 0003"没有开发者模式"的例外）。它不对外分发，正式构建不编译这些代码路径。

**任务层与派发**
18. **去掉配件令牌，改为配件在请求头里自报标识**（v0 §4「通道」）。令牌不是安全措施，只多出签发、保存、重发几个故障点；socket 不变。
19. **v1 的后台请求也同步调用，不能马上执行就立即返回原因码**（v0 §4「同步与异步」）。被打断时返回 `interrupted`、由配件重试，主控不保留部分输出，也不保证它回到队首（v0 §6「打断」）。异步编号协议推到 v1.x。
20. **"用户在等"的请求遇到排队和冷加载时等待并收到进度事件，不再立即返回原因码**（v0 §4"不能立即执行时，马上返回原因码"）。立即返回只限需要用户决定、任务做不了、输入超长这几类；打分端点例外，模型没准备好就立即返回 `not_ready`（内存不够则 `needs_user`），因为交互式的打分等不起。
21. **配件不再指定输出长度，只报条目数**（v0 §4"以及不超过上限的输出长度"）：主控按任务参数算出上限并覆盖 `max_tokens`。批大小（一次请求的条目数上限）仍是任务参数。
22. **`GET /tasks` 只列请求方配件自己的任务，并附全机后台状态**（v0 §4"列出所有任务"）。
23. **主要任务的标记写在配方的任务表里**（v0 §4"配件登记时标明"），安装器在配件装上之前就能读到。
24. **"专用模型与后台让路"改为统一的"交互中"判定**（v0 §6）：任何路径最近 N 秒有"用户在等"的请求或预热发起，都不接新的后台请求；打分请求同样按粗估规则考虑打断后台请求。
25. **功耗档、电池和过热规则不作用于专用模型**（v0 ADR 0006"施加功耗规则"）。专用模型只服务"用户在等"的打分请求。
26. **预热收窄，"安静时刻"重新定义**（v0 §5 通用预热、CONTEXT v0「安静时刻」"没有用户在等的请求、相关配件也空闲"）。v1 的预热改为租约：配件在交互将要开始时发起、需要期间续期，期间不因闲置卸载；安静时刻改为"连续 M 分钟不处于交互中"，预热续期不算交互中。
27. **任务状态的"暂停中"只用于整个任务都做不了；用电池、低电量、过热、等内存改由新增的"全机后台状态"报告，等网络并入"下载中"，枚举加上"需要换代"**（v0 §9「任务状态」）。
28. **电源规则三处改动**（v0 §6「功耗与电源」）：一次性用电池许可改为请求字段 `allow_battery`，配件只在用户亲手启动的批量工作上带，主控不再跟踪"插上电源或做完就失效"；配方的"用电池也做"v1 先不填；过热从"放慢后台"改为"thermalState 到 serious 及以上时暂停后台"。
29. **功耗档的第三档改名为"静音"**（v0 叫"安静"），避免和"安静时刻"撞词。

**安装、更新与回退**
30. **v1 先发主控 DMG，首次运行时把自己装到固定位置、预检、一屏同意；按配件定制图标推到 v1.x**（v0 §8「只有一个安装包」）。
31. **只有常驻配件由主控启动并保活，后台入口推到以后**（v0 §8「只有一个登录项」；v0 §11 曾计划把一个配件的后台工作改为后台入口加异步请求）。需要后台运行的配件在 v1 作为常驻配件由主控保活。"只有主控有登录项"不变。
32. **引擎包单独回退**（v0 只保留旧底座，引擎没有回退路径）：换了引擎包的发布，新配件版本也要在上一版引擎包的组合上验证；引擎包冒烟失败或熔断时只退回上一版引擎包。
33. **回退只能落在已验证的组合上**（v0 §8 撤回时"有保留着的旧底座就回退过去"，没有条件）：回退之后每个在装配件版本都必须在所用组合上已验证，否则相关任务"暂停中"。
34. **配件更新只在新版本报告正常之前失败才回退，快照由主控恢复**（v0 §12"保留上一个版本以便回退"）。数据库只有正向迁移，报告正常之后再退回旧版反而会坏数据。
35. **冒烟检查是后台工作，在安静时刻做；首次冒烟检查在启用新组合之前做、不受用电池限制，检查新引擎包时先停旧引擎再检查**（v0 未规定时机和做法）。小内存档装不下两份底座。
36. **换代扩大到专用模型，切换顺序改为小内存档先卸旧再冒烟**（v0 CONTEXT「换代」只指换底座；v0 §8"先下载，再做冒烟检查，然后在没有用户在等请求的时刻切换"）。
37. **撤回不受自动更新开关限制**（v0 §8"用户可以关掉自动更新"，没有例外，撤回随配方更新送达，开关关掉就收不到）。撤回清单随检查更新取回、立即生效，不需要先装新版本；开关只管要不要安装新版本。
38. **新增换机规则**（v0 只在 §12 列了迁移助理授权的实测）：换到内存不同的 Mac 时提示下载新硬件档的底座。
39. **v1 只开一个下载通道**（v0 §3 双站同名发布），第二个站点在 v1.x。

**配件**
40. **每个 Python 配件自带一份 Python**（v0 §5「配件运行时」，ADR 0010）。v0 §5 留下的"配件运行时能否和 oMLX 共用一份 Python"，结论是否。同时放宽 v0 §5"配件仍只用标准库"：尽量只用标准库；确实需要第三方包时，随配件 .app 签名打包、版本固定，由该配件版本的评测覆盖。
41. **v0 §11"现有配件的接入"移出核心设计**，换成通用的"配件接入契约"（§11）。各配件的具体需求、数值和接入改动（包括 v0.1 对它们的几处调整）见 [docs/research/accessory-requirements.md](research/accessory-requirements.md)。

44. **luoke-mem 在 v1 就作为组件配件由主控安装**（v0 §1、§11"第一版随 luoke-mail 发布"；顶层 ADR 0014，2026-10-10）。它有按需打开的界面和卸载用的命令行；别的配件经主控打开它的界面；卸载时的"一起忘掉"用主控装的这一份执行。（修订 2026-10-14，顶层 ADR 0015：它开始在安静时刻经主控用模型归纳理解，"没有模型任务"不再成立，见 §11。）

**推迟（v1 不做）**：换代（范围有改动，见第 36 条）、省内存模式（其中"主动建议"推到以后）、配方独立通道和签名、第二个下载站点、统计非劣检验、CI、每日核对，见 §0.2。

**从"已定"改为"以后再定"**：维持期是否保留、定多长（v0 §8 定为 6 个月）；模型层（v0 §4 只读模型层是要做的）、复用、后台入口、自动上报，现在都是"以后可能做"（§1）。

**待办收窄**（v0 §13）：许可只查 v1 用到的模型，其余进配方前再查；关掉 SSD 缓存后不再测 SSD 冷读 KV；16 GB 档的底座速度并入 §13 第 1 项的重测；专用模型改为"配件运行期间保持加载"（§5），不再在"wired 额度"和"交互时保温"之间选。

### 0.4 v1 必须一次做对的

这些以后改代价很大，v1 就要定死：主控的 bundle id、安装位置 `~/Applications/螺壳主控.app`、登录项机制、主控环境路径（与 `~/.luoke` 等用户数据分开）、socket 路径；配方格式里"组合"的粒度（一个模型文件 + 一个引擎包版本）、版本号、`min_hub_version`、`revoked`、模型分配的角色字段，以及预留的签名字段。配件这一侧，已发布配件的 bundle id、Team ID 和安装路径同样不能变（变了会丢辅助功能等系统授权），这写在配件接入契约里（§11）。

## 1. 目标与边界

**目标**：给不折腾的普通 Mac 用户一个精品的本地 AI 体验。思路像 LEGO SPIKE 的主控：用户不用挑芯片和电池，配件插上就能用；又像 Mac：默认就很精致。技术上没有新发明，价值在于集成得好，以及实验室的实测证据。

**主控管的事**：模型和它们占用的资源（内存、GPU、功耗、磁盘）；配方；配件的安装、更新、卸载和启动。

**明确不管的事**：用户记忆的内容和界面（归 luoke-mem，它是主控第一版就安装的组件配件，顶层 ADR 0014；主控只负责装它、更新它、替别的配件打开它的界面）；配件之间怎么互相调用；第三方配件；Mac 以外的平台；任何针对某一个配件的特殊处理。

**以后可能做、现在不做的事**：模型层（只读列出已装模型），以及是否把它开放给本机其他工具；复用用户已有的模型文件；借用用户自己的引擎服务；嵌入、语音识别等一直加载的小模型；"仍然加载"；断点续做；后台入口；共享的配件运行时；配件之间的依赖；自动上报；省内存模式的主动建议；基于代码签名的调用方身份；跨配件的统一数据删除；多账户内存归因；远端引擎（局域网里另一台主控、或用户自己部署在云端的主控，主控对主控，打分留本机，见 [research/remote-engine.md](research/remote-engine.md)，2026-10-13 定为以后）。

## 2. 总体结构

```
配件（各自带运行环境，遵守 §11 的接入契约）
   │  任务层：Unix socket（主控环境里本账户 0700 文件夹）
   │  请求头自报配件标识；OpenAI 兼容请求（一律流式），任务名在路径里；打分任务另有打分端点
   ▼
主控（~/Applications/螺壳主控.app，唯一登录项，菜单栏状态灯）
   ├─ 派发：两级请求、打断、交互中/安静时刻、功耗与电源、内存预算
   ├─ 配方：随 .app 发布；模型清单、引擎包清单、模型分配、按组合的任务参数和底座参数、依据、已验证版本、撤回
   ├─ 安装器/更新器：主控自更新、按发布清单装引擎包和配件、撤回清单、模型下载先问
   ├─ 常驻配件的启动与保活（经 NSWorkspace，系统权限归配件自己）
   └─ 引擎适配器
        └─ 引擎包（钉版本、不改代码、实验室重签公证）
             ├─ oMLX 服务（独立 base-path，127.0.0.1 随机端口 + 随机密钥）── 底座
             └─ mlx-lm 工作进程（主控监管，用引擎包里的 Python）──────── 专用模型
主控环境：~/Library/Application Support 下，每账户一份
用户环境（用户自己的 oMLX、~/.omlx 等）：只看进程的内存占用，不读不改
```

共享模型的请求走派发，专用模型的请求直连（ADR 0006）。

## 3. 配方

**内容**
- **模型清单**：每个文件的哈希、上游版本、量化方式、许可、能否再分发、下载地址列表。
- **引擎包清单**：每个引擎包版本的哈希、下载地址、内含的 oMLX、Python、mlx、mlx-lm 版本、支持的 macOS 范围，以及启动清单（§5）。启动清单属于这个版本，不能单独改。
- **组合**：一个模型文件（哈希）加一个引擎包版本，与硬件档无关。
- **模型分配**：每个硬件档列出这一档用哪些组合（底座一条，每个专用模型一条），每条带角色：
  - 现役：正在用的；每档同一时间只有一个现役底座。
  - 上一版：上一个引擎包版本的组合，是引擎包回退的落点（§8）；保留到下一次换引擎包的发布，之后移出配方。
  - 维持中（v1.x）：维持期里的旧底座。
  - 已退役：仍在配方里，已装用户可以继续用，但不再收到新配件版本。
  仍在配方里的任何条目都不算"配方外"。
- **任务表**：每个任务属于哪个配件、是不是主要任务、调用方式（生成或打分）、延迟要求（如有），以及每个配件版本在每个组合上的任务参数（与内存有关的按硬件档细分）。主控按请求头里的配件版本取参数。
- **底座参数**：每个组合上与任务无关的设置，例如思考开关怎么映射到模板参数、默认采样、`response_format` 的写法。
- **已验证版本**：每个配件版本在哪些组合上达到了及格线，即这个版本在该组合上没有标"不支持"的每个任务都达标；"不支持"按"配件版本 × 任务 × 组合"记录，写进依据。配方至少保留上一次发布的配件版本的这些记录（含当时的任务参数）。
- **依据**：每个"配件版本 × 任务 × 组合"的一句大白话质量结论，以及摘要（评测集条数、硬性条目数、评测日期、引擎包版本）和完整证据的哈希。界面上取本机在装的配件版本那一条。逐条结果和及格线留在实验室仓库，不下发。
- **发布清单**：这次发布的版本号，包含哪些配件版本和引擎包版本。
- **撤回清单**（`revoked`）：发布时的快照；v1 主控还会随检查更新取回最新的撤回清单，两者取并集（§8）。
- **`min_hub_version`**、配方版本号、预留的签名字段。

**规则**
- **封闭**：配方外的模型和任务主控一律不用，用户也加不进来，没有逃生门；代码开源，真想 hack 的人可以自己改（ADR 0003）。实验室自己开发用"实验室构建"（§7）。
- **模型来源**：实验室从上游官方权重自己量化（oQ 格式用 oMLX 自带的 `oq.py`）。v1 只开一个下载通道，以国内用户为主就用 ModelScope；配方里每个文件的下载地址写成列表、以哈希为准，第二个站点（Hugging Face 同名仓库）在 v1.x 加上。许可不清楚的模型不收。主控、配件、引擎包和更新源的托管另定，见 §13 第 1 项。
- **发布与签名**：v1 的配方放在主控 .app 的 `Contents/Resources` 里，随主控发布，完整性由代码签名和公证保护；主控记录配方版本号，不拒收旧配方（否则用户无法手动装回旧版主控）。v1.x 开独立的配方通道，届时配方由实验室签名（私钥放在硬件密钥或 Secure Enclave 里，P-256），版本号只增不减、主控拒收比本地旧的配方。
- **新任务随发布车上线**：先评测，写进这次发布的配方，再和配件同车发布；没有评测集的任务进不了配方。
- **任务参数包括所有随模型变化的数**：凡是以 token 或 nats 为单位的常数，一律是任务参数，例如打分任务的接受门槛和奖励常数；输出上限写成"每条目预算 + 固定开销"，配件只报条目数、主控算出上限；批大小（一次请求的条目数上限）；输入上限按字符给出（配件数不了 token）；是否思考也是任务参数，某个组合做不到思考时这个任务在那里标"不支持"，不悄悄改成不思考（ADR 0005）。与内存有关的任务参数（例如输入上限、批大小）按硬件档另给取值，评测时用这个组合所在各档里最紧的取值。
- **证据的记录格式**（实验室仓库里）：配件版本、任务、评测集哈希、组合（模型文件哈希、引擎包版本）、量化方式、底座参数和任务参数、机器与芯片、日期、逐条结果。

## 4. 任务与任务层

**任务**
- 配件只说任务，不点名模型。提示词和输出格式写在配件里、随请求发来，必须在用到它的各个组合上都能用；主控不懂业务内容（ADR 0005）。
- 一个配件版本的一个任务在同一个组合上只有一套任务参数（与内存有关的按硬件档细分）和一份证据。需要两种做法（例如思考和不思考）就定义成两个任务；是否思考由配件在定义任务时提出。
- 每个任务都要有评测集（§7）。没有评测集的任务进不了配方，主控不会服务它；暂时没有评测集的功能，配件先用非 AI 的做法或隐藏。
- 主要任务和可选任务的标记写在配方的任务表里，安装器在配件装上之前就能读到。

**任务层**（唯一推理入口）
- **通道**：Unix domain socket，放在主控环境里一个只有本账户能进的文件夹（0700）。配件在请求头里自报标识和版本（例如 `X-Luoke-Accessory: <配件名>/<版本>`），主控按配方的任务表核对任务归属。未登记的调用方不受支持，以后可能失效（ADR 0007）。配件的开发构建可以用环境变量 `LUOKE_HUB_SOCKET` 改连实验室构建的 socket。
- **端点**：
  - `…/tasks/<任务名>/v1/chat/completions`：生成任务，请求体沿用 OpenAI 格式，**一律流式**（`stream: false` 会被拒绝），这样排队和冷加载期间主控能用约定的 SSE 事件（`luoke.progress`）告诉配件还活着。答复的 `model` 字段写这次实际用的组合。
  - 打分端点：输入上下文和候选，返回 log 概率、实际用的组合和耗时。打分工作进程按配件保留最近几条前文的 KV 快照（条数是任务参数），新请求的前文以其中一条为前缀时复用，只算增量；快照只在内存里、随模型卸载清掉，命中与否只影响耗时不影响结果，回复里报是否命中（输入法同一句里"前文 + 已定的词"反复出现，2026-10-11 定）。它不等待加载：模型正在加载或在等内存压力恢复时立即返回 `not_ready`（附 `retry_after`），因内存不够加载不了时返回 `needs_user`（附占用者名单）；配件据此跳过这次打分或稍后重试。
  - `GET /tasks`：只列请求方配件自己的任务、任务状态、任务参数，并附全机后台状态。
  - `POST /accessory/ready`：配件完成启动时的全部数据迁移后调用，这才算向主控**报告正常**（§8 配件更新据此判断）。
  - `POST /accessory/exiting`：配件正常退出前调用。主控据此不再重启它（直到下次登录）、不计入 §8 的异常退出次数、卸载它的专用模型；没有先调用就退出的，才算异常退出。
  - 预热端点：立即返回，不等加载。接受时返回 `{accepted: true, lease_id, expires_in}`，主控加载模型并在租约期内不因闲置卸载；不接受时返回 `{accepted: false, code}`，code 取 `task_unavailable`、`unsupported` 或 `deferred`（低电量、内存压力或内存不够时暂不预热），配件不把预热被拒展示给用户。续期要带上 `lease_id`；不带 `lease_id` 或租约已失效的调用算一次发起。只有被接受的发起才算交互事件；主控重启后收到不认识的续期，按新的预热处理，但不算交互事件。
  - `PUT /accessory/resident`：配件声明自己要不要作为常驻配件、登录时由主控启动；可以随用户设置变化随时调用。
  - 打开记忆界面：调用方 `open luoke://memory`（可带 `?note=`、`?view=recent`），由主控本体接住、用自带的 Python 起界面（V1 §6）。（beta0 时是按 bundle id 打开单独的 `ai.luoke.memory` .app；10-16 起并进主控。）（2026-10-10 与 luoke-mem 商定时还有第二种——主控跑它的 `ui` 命令、把地址转发给调用方的 `POST /accessories/luoke-mem/ui`；2026-10-16 负责人按顶层越界自查定删掉：主控不替配件转发界面，luoke-mail 改用 `open -b ai.luoke.memory`。）
- **推理字段白名单**：请求体里配件只能决定消息、输出格式和条目数。主控按任务参数的"每条目预算 + 固定开销"算出输出上限并强制执行，配件填的 `max_tokens` 会被覆盖；条目数不得超过批大小；思考开关、采样、模板参数一律由主控按任务参数和底座参数覆盖；消息里的特殊 token 串由主控按底座的分词器中和；主控自己按 OpenAI 格式校验消息结构，不合法的请求在主控处拒绝，不转发给引擎；输入超过字符上限直接拒绝，截短由配件按上限自己做。
- **调度字段**（放在请求头）：请求等级（"用户在等"或"后台"）；`allow_battery`（只用于用户亲手启动的批量工作）。取消就是关闭连接。
- **执行与答复**：
  - "用户在等"的请求能执行就执行；排队、冷加载（包括主控重启后底座重载）都是正常等待，期间发进度事件。
  - v1 的后台请求在三个条件同时满足时接下：不处于交互中；没有别的后台工作在占引擎（包括功耗档的间歇，§6）；全机后台状态按 §6 现算为运行中，或者暂停原因只有"用电池"而请求带 `allow_battery`（或任务标了"用电池也做"）。接下后必要时冷加载底座，同样发进度事件；条件不满足就立即返回 `busy` 或 `paused` 和 `retry_after`，主控不为后台请求排队。被打断时返回 `interrupted`。v1.x 改为提交后拿编号、凭编号查询的异步协议，主控队列只放在内存里。
- **线上格式**（socket 路径、请求头名、任务名写法、各端点的 JSON 字段、状态码）以 V1 §2 为准，2026-10-12 起冻结为对外约定版本 1，只加不改。
- **原因码的载体**：开始流式答复之前的拒绝，用 HTTP 状态码加 JSON 体 `{code, message, retry_after}`；开始之后，用终止事件 `luoke.error`（字段相同），配件丢弃已收到的部分输出。
- **原因码**（附一句中文说明和建议的 `retry_after`）：
  - `needs_user`：要用户决定，例如内存不够，附上谁在占内存。
  - `paused`：全机后台状态是"已暂停"（只用于后台请求），附原因。
  - `busy`：v1 后台请求遇到交互中或引擎已被别的后台工作占用。
  - `interrupted`：后台请求被打断。
  - `task_unavailable`：任务状态不是"可用"（暂停中、需下载、下载中、需要换代），附任务状态和原因。
  - `unsupported`：任务在这台 Mac 上不支持，原因取自配方里这个任务在本档的依据文案，或配方层面的原因（例如本档不设底座）。
  - `not_ready`：打分模型正在加载，或在等内存压力恢复。
  - `engine_failed`：引擎在请求进行中崩溃、超时或加载失败，两种等级都适用。
  - `deferred`：只用于预热，主控暂不预热。
  - `input_too_long`：输入超过字符上限。

**修订（2026-10-16，算向量）**：10-16 提议、10-19 认可，全生态的模型推理和权重统一归主控（顶层 ADR 0018），digup 搜索去掉自带模型、改经主控拿向量。任务层加一个调用方式"嵌入"（`kind: embed`，端点 `/v1/embed`，线上格式见 V1 §2），只加不改、契约版本仍是 1。它走专用模型那条路（ADR 0006）：模型跑在主控监管的工作进程里，不走引擎、不排队、配件运行期间常驻（空闲 10 分钟停、下次用到再起，见 §3 专用模型工作进程的生命周期），和打分同构；区别是无状态（没有前缀快照）、不探针、不标"较慢"，以及**有请求等级**：打分只服务打字（一律"用户在等"），而嵌入大多是建索引这种批量活，所以不带 `X-Luoke-Priority` 时按后台、照后台的规矩接纳和歇（§6），搜索时的查询才带"用户在等"。冻结的面尽量小：只收调用方加好前缀的文字，满维、float16；截维、图片和声音以后作为新增字段加。**向量空间**（应 digup 加）：配件存的向量要能跨主控升级接着用，可组合名（`model`）按契约不透明、不能解析，所以嵌入任务另给一个只比相等的 `vector_space`（`GET /tasks` 和每次答复都带）；它由实验室在发布时定——新向量对参考向量集仍然余弦 ≥ 0.999 就不变，否则加一——换引擎、换量化都不必让用户重建索引，真变了配件也只重算向量。评测口径：对 digup 的参考向量集余弦 ≥ 0.999（和它已有的索引兼容），是这个任务的硬性条目。在评测通过、模型分配到档之前，配方模板里有任务但没有模型，主控对它答 `unsupported`，不服务——上面"没有评测集就进不了配方"照旧。

## 5. 模型、硬件档与引擎

**硬件档与模型**
- **分档**：只按统一内存分档；芯片代数和功耗模式只影响速度，不分档；只做 Apple Silicon Mac。v1 的配方只收经过确认装得下的硬件档（约三档），具体边界是配方内容。确认方法：先用公式估算"权重 + 专用模型 + 最长请求的 KV + 引擎开销 + 热缓存上限 ≤ GPU 工作集上限 − 余量"；16 GB 档以 16 GB 测试机实机为准；没有实机的中间档，在 M5 Max 上用 oMLX 的 custom 内存天花板加占位进程来近似（绝不用 `sysctl iogpu.wired_limit_mb`，见 CLAUDE.md 安全红线），在证据里注明是模拟，并按公式留更大的余量。
- **底座**：每档同一时间只有一个现役底座，这一档上所有生成任务都由它来做；某个生成任务在底座上达不到及格线，就在这一档标"不支持"，不轮换第二个大模型（ADR 0004）。维持期里旧底座以"维持中"的角色暂时并存（v1.x，§8）。
- **专用模型**：只用于打分任务（任务表里调用方式为"打分"）。换专用模型和换底座一样，属于换代（v1.x）；撤回后的替换除外（§8）。
- **8 GB 的 Mac**：不设底座，只跑专用模型，也就是只能用只依赖专用模型的配件。实验室没有 8 GB 的机器，速度靠本机冒烟检查和"较慢"状态兜底。
- **省内存模式**（v1.x）：用户自己打开，把这台 Mac 当低一档来用，下载照样先问。

**引擎**（ADR 0001）
- v1 只有一个**引擎包**：钉住版本、一行不改的 oMLX，连同它自带的 Python、mlx 和 mlx-lm。底座跑在 oMLX 服务里；专用模型跑在主控监管的 mlx-lm 工作进程里，用引擎包里的 Python，以库的方式调用（不用 `mlx_lm.server`）。主控和工作进程之间只用主控创建、继承给它的管道或 socketpair，工作进程不监听任何端口，它的 stdout 和 stderr 由主控接收并经过去内容过滤。工作进程不放进主控进程（它出故障不会带崩主控；v1 里主控退出时它也自行退出，见 §10，以后可以做到主控重启时不打断专用模型）。
- 配方里的引擎包版本同时管两条路；升级引擎包时，要回放所有配件的评测集，包括只用专用模型的配件。
- **oMLX 0.7.0 的启动清单**（每个引擎包版本都要逐条实测，写进引擎包清单）：
  - `--base-path` 指向主控环境；只听 127.0.0.1，用随机端口；每次启动生成随机 `--api-key`；
  - 缓存二选一（见下）：`--no-cache`；或者在 `{base_path}/settings.json` 里设 `cache.hot_cache_only: true` 并传 `--hot-cache-max-size <N>GB`（不设大小就等于没有缓存）；
  - `--no-hf-cache`，不扫描用户的 Hugging Face 缓存；
  - `--memory-guard-gb` 传入主控算出的预算；
  - 日志级别取能通过 §10 出错路径标记测试的最高级别（不得用 trace，它会记下完整消息内容；oMLX 0.7.0 的 422 处理还会在 WARNING 级记下出错字段的原值）；error 级也泄露的引擎包版本不得进配方；
  - 不传 `--mcp-config`；启动前清掉 `HF_*`、`OMLX_*` 环境变量；
  - oMLX 会把命令行参数持久化进 `{base_path}/settings.json`，所以主控每次启动引擎前整份重写这个文件；每个引擎包版本用各自的 base-path（主控环境下按版本分目录）。
  - 管理面板和 websearch 路由关不掉，但都要那把随机密钥。
- **缓存**：第一版用 `--no-cache`。实测 0（[experiments/coexistence.md](experiments/coexistence.md)）表明热缓存对真实分拣命中 0%：oMLX 对混合结构模型把缓存块放大到 2048 token，系统提示词不足一块；它还多占 1–2 GB 内存。
- **内存保护**：oMLX 自带的内存保护会自己拒绝请求、按 LRU 驱逐模型、硬压力下中止全部请求；它的 balanced 档在 16 GB 机器上根本不让加载 5.8 GB 的底座（实测 0），所以主控必须传 `--memory-guard-gb`。传入后 oMLX 实际可用 = (天花板 − 2 GB) × 0.95，预算要按这个倒推；底座和专用模型的占用按实验室实测的 wired 峰值（含最长请求的 KV）写进配方，不按文件大小估（实测 1：9B 4-bit 文件 5.8 GB，推理时比空机多 10 GB；gemma 4 经 mlx-vlm 加载约为文件的两倍）；主控看内存以 `vm_stat` 的 swapouts 增量和 wired 为准，`memory_pressure` 的空闲百分比受页缓存影响，只作参考；`--memory-guard-gb` 会让它不再跟踪其他程序的内存，天花板变成固定值，所以主控在预算变化时（专用模型加载或卸载、其他引擎占用变化、内存压力）通过 oMLX 的管理接口更新这个值；如果在 oMLX 运行期间更新不生效，就只在启动时传一个保守值，动态部分完全由派发负责。它的拒绝、驱逐和全部中止一般按"内存不够"处理（返回原因码，全机后台状态"等内存"），不计入熔断（例外见 §12）。
- **签名**：引擎包里的二进制用实验室的 Developer ID 重签并公证（不改代码），和主控、配件同一个 Team ID。
- **向上游提的需求**：中断时保留已算好的 KV；按请求等级接纳（#3047）；prefill 块大小可配置。

**配件的 Python**
- 每个用 Python 写的配件，在自己签名公证的 .app 里自带一份 Python（例如 python-build-standalone），这份 Python 的版本跟着配件版本走（ADR 0010）。配件不依赖 `/usr/bin/python3`（在干净的 Mac 上会要求先装命令行开发者工具）。
- 配件尽量只用标准库；确实需要第三方包时，随配件 .app 签名打包、版本固定，由该配件版本的评测覆盖。

**驻留**
- 模型用到才加载，闲置一段时间后卸载；v1 先用一个全局的闲置时长，v1.x 再按硬件档定。
- **v1 的预热**：配件在交互将要开始时（例如界面打开时）发起预热，主控加载模型，需要期间配件定期续期，模型不因闲置卸载。续期不算交互中，也不挡后台请求；内存压力（warn、critical）和低电量模式优先于预热。
- 专用模型在它的配件运行期间一直保持加载；只有内存压力到 critical 级、卸载底座后仍不够时才卸载（§6）。
- v1 主控重启即重启引擎：专用模型在它的配件运行时立即重载（专用模型通常很小，重载很快）；底座不主动重载，在下一次请求或预热时冷加载。

## 6. 派发与资源

**请求等级与交互判定**
- 每次请求标"用户在等"或"后台"，按请求标，不按任务标。"用户在等"只用于有人正盯着结果的请求；用户亲手启动、自己不再盯着的批量工作算"后台"，可以带 `allow_battery`。打分请求同样带等级，通常是"用户在等"。（与 luoke-mail 2026-10-13 说清：用户点了"同步"、盯着进度条等那几封到几十封，逐封标"用户在等"是对的——他确实在等；用户离开页面后剩下的改标"后台"。代价由用户自己承担：16 GB 上会加载底座、打字期间变慢。）
- **交互中**：任何路径（包括专用模型）最近 N 秒有过"用户在等"的请求，或者最近 N 秒有配件发起了预热（续期不算）。
- **安静时刻**：连续 M 分钟不处于交互中。
- 派发、自动安装、冒烟检查、主控自更新都只引用这两个判定，不另设计时器；唯一的例外是下面"打分任务与后台共存"做法 1 的 K 分钟后台接纳窗口（如果采用），它只作用于后台请求的接纳。N、M 由实测定；主控启动后，"连续 M 分钟"从启动时刻开始计。

**后台工作**
- 后台工作是不为答复"用户在等"而占用 GPU 的工作：后台请求，以及所有冒烟检查。它们共用"同一时间最多一项在引擎里"的名额，受功耗档和电源规则约束；首次冒烟检查例外，不受用电池的限制（§7）。
- 下载和安装不占 GPU，不算后台工作。用户在一屏同意、存储页或换机提示里亲手同意的下载，同意后立即开始，交互中也不暂停；自动更新带来的下载，以及替换正在运行的配件或引擎包的安装，只在安静时刻进行。两者都遵守网络规则（§12）。

**v1 的派发**
- 派发决定一条共享模型请求什么时候跑、要不要为"用户在等"的请求打断正在跑的后台工作（用哪个底座由这台 Mac 的模型分配决定，不由派发决定）。
- 同一时间最多一项后台工作在引擎里；交互中不接新的后台请求（§4）。
- "用户在等"的请求（包括打分请求）到来时，主控粗估后台工作还要多久（剩余 prefill ÷ prefill 速度 + 剩余 token ÷ 解码速度），和打断的代价（oMLX 约 2 秒的断开检测，加上最多一个 prefill 块）比较：剩余更短就让它跑完，否则断开它，后台请求返回 `interrupted`，由配件重试。打分请求本身不排队，粗估只决定后台工作的去留。
- **打分任务与后台共存**（实测 0 已定）：底座在内存里打字就已受影响（单次打分 p90 涨 1.3–2 倍），后台 prefill 时涨 3–7 倍，而打断要约 11 s（2 s 断开检测加当前 prefill 块），救不了打字。所以三条一起用：
  1. 后台接纳规则：任何路径最近 K 分钟有过打分请求时，不接新的后台请求（只影响后台接纳，不改变交互中和安静时刻），K 取几分钟量级，上线后按用户停手的分布调；
  2. 后台请求按硬件档限制输入长度，慢机器上每条请求控制在几十秒以内，配件分段提交（M1 上 9B 的 8k prefill 要 100 s）；
  3. 16 GB 档的后台工作只在安静时刻进行，底座也只在那时加载、用户一回来就卸载（9B 常驻时系统空闲只剩 10–20%）。"用户在等"的请求不受此限：任何时候都能冷加载底座（§4，用户自己在等，12–19 s 的加载和期间打字变慢是他选的），但 16 GB 档上做完之后底座不常驻——下一条打分请求一到、或闲置超过闲置时长，就卸载；32 GB 以上常驻。

**功耗与电源**
- **功耗档**（全速、均衡、静音）管后台工作和本机端点的请求；打字和配件里用户手动点了等结果的请求永远全速（ADR 0011，2026-10-22 改：原来只管后台）。v1 用间歇实现（oMLX 不能限速）：每项后台工作结束后，主控在它占用 GPU 时长的 0 倍（全速）、1 倍（均衡）、3 倍（静音）时间内不接新的后台工作，期间后台请求返回 `busy` 和剩余间歇作 `retry_after`；本机端点的请求照旧算"用户在等"、排在后台前面，但每条做完，下一条先挂着等它用时的同一个倍数（最多 10 分钟）再开始；静音档在 thermalState 到 fair 时就暂停后台工作。切档立即生效，默认均衡。
- **电池**：后台工作默认只在接电源时进行。设置里"用电池时：暂停后台（默认）/ 也运行"和功耗档并列显示。两个例外：请求带 `allow_battery`（配件只在用户亲手启动的批量工作上带）；配方给某个任务标了"用电池也做"（任务参数，v1 先不填）。
- macOS 低电量模式下后台工作一律暂停，"用户在等"照常但不预热；`ProcessInfo.thermalState` 到 serious 及以上时暂停后台工作。
- **全机后台状态**：运行中，或已暂停（附原因：用电池、低电量、过热、等内存）。它通过 `GET /tasks` 告诉配件，不混进单个任务的状态。转为已暂停时：原因是用电池或低电量的，正在跑的后台工作跑完，不再接新的；原因是过热或等内存的，正在跑的后台请求按打断处理，返回 `interrupted`。
- 专用模型只服务"用户在等"的打分请求，功耗档、电池和过热规则对它不起作用；主控对它管的是加载、内存和进程监管。

**内存**
- **从不硬挤**："等内存"不是锁存状态，每次后台请求到来时现算：底座已加载，或者按当前预算放得下底座且内存压力正常（恢复后已满几分钟），就视为运行中；否则返回 `paused`（等内存），由配件稍后重试。内存压力 warn、critical 期间以及恢复后的几分钟内，全机后台状态为"已暂停（等内存）"。"用户在等"的请求：底座已加载就照常执行；需要冷加载但预算放不下或压力还没恢复时，立即返回 `needs_user` 和占用者名单（包括其他 AI 引擎），由配件在当前界面告诉用户，用户腾出内存后重试。oMLX 内存保护中止进行中的请求时，后台请求返回 `paused`（等内存），"用户在等"的请求返回 `needs_user`。
- **安全底线**：主控永远不调高系统的 wired 内存上限，在 macOS 默认的 GPU 工作集上限内工作；检测到别人已经调高了它，预算取"默认上限"和"物理内存减去别人已占的 wired 再留余量"中较小的一个；主控不拿管理员权限，结构上也改不了它（ADR 0007）。
- **专用模型优先**：先给专用模型留空间，再算底座放不放得下；热缓存（如果用）也算进预算。
- **内存压力**：订阅系统的内存压力通知。warn 级：卸载闲置的底座，正在跑的后台请求按打断处理；critical 级：当前"用户在等"的请求做完后卸载底座，仍不够才卸载专用模型。压力恢复正常并持续几分钟、确认内存确实回收后，才重新加载。
- **观察用户环境**：只看进程列表里其他 AI 引擎的内存占用，算进预算；进程列表里看得到的其他账户的引擎进程，也按"其他 AI 引擎"计。不读它们的文件，不改它们的设置。

## 7. 质量：评测与验证

**评测集**
- 每个配件的每个任务都要有评测集，这是成为配件的条件。v1 每个任务的评测集 20–40 条起，包含硬性条目；多步任务（例如输入法的逐词重排、输出不合格时重问）用配件自带的评测程序。
- 评测集由配件出，实验室来跑。

**及格线**
- 三层：硬性条目一条都不能错；总分不低于配件定的底线；发配件新版本或换组合时，不比之前已验证的版本或组合明显差。
- v1 的第 3 层：硬性条目零回退，总分不低于之前已验证的结果减去一个容差，并输出逐条差异报告，负责人看过再放行。一个任务在某个组合上从"支持"变成"不支持"也算回退，要负责人在差异报告里确认。评测集扩到约 200 条后，v1.x 再换成统计非劣检验。

**延迟要求**
- 任务可以在定义时声明延迟要求，写清三样：实验室关卡在哪台机器上、用什么口径、什么数值；以及给用户机器用的本机阈值（主控能测的单次请求 p90）。
- 具体配件的延迟要求是配方任务表里的数据（现有配件的数值见 [accessory-requirements.md](research/accessory-requirements.md)）。实验室关卡放在自有的慢机器上（目前是 16 GB 测试机的 M1 和 32 GB 测试机的基础款 M4）。
- 用户机器上，冒烟检查实测本机速度：声明了延迟要求的任务，本机实测超过本机阈值，任务状态就显示"可用，但在这台 Mac 上较慢"，附实测数字，怎么处理由配件决定；没有声明延迟要求的任务不标"较慢"。

**发布前必须验证**（ADR 0008）
- 每个配件版本，哪怕只改了提示词，都要在它的任务用到的每个组合（各硬件档角色为"现役"的模型分配里的）上达到及格线，写进配方的已验证版本后才能发布；主控只安装已验证的版本。
- **换了引擎包的发布**，新配件版本还要在上一版引擎包的组合上验证，这样引擎包可以单独回退（§8）。代价是这几项任务再评一轮；不换引擎包的发布不再补验上一版。
- 质量在一台机器上评；再在每代芯片（M1、M4、M5）上回放一个固定子集，核对逐条结果一致，因为不同芯片走不同的 Metal 代码路径，温度为 0 也不保证逐字一致。硬性条目出现不一致，这个版本不发布；其他条目不一致的记进证据，由负责人在差异报告里判断。实验室没有实机的芯片代（M2、M3）不做回放，在证据里注明。
- v1 由负责人手动跑发布脚本，自动判定第 1、2 层并生成差异报告；CI 自动关卡以后再做（能跑大底座的只有负责人日常用的 M5 Max）。先实测一次完整评测的墙钟时间，再估发布节奏。

**实验室构建**
- 实验室自己开发和调试用的主控构建：不同的 bundle id，独立的主控环境和 socket 路径（不会和同一台机器上的正式主控抢）；可以运行未验证的配件版本。v1 从它自己的主控环境里的固定路径读取本地配方；v1.x 配方开始签名后，改为内置实验室测试公钥、对本地配方验签，而不是关掉验签。它不对外分发，正式构建里不编译这些代码路径。

**用户机器上**
- 只做冒烟检查：能加载、能输出合法格式，顺带实测本机速度。冒烟检查是后台工作，在安静时刻进行，占用后台工作名额。
- **首次冒烟检查**：装好或换了组合（包括引擎包更新）之后，在启用新组合之前做。新装时任务状态是"下载中"，子原因"正在检查"；这次检查不受用电池的限制。检查新引擎包时：先停接后台请求、等正在跑的后台工作跑完，再停掉旧引擎（卸载模型、确认内存回收），然后用全部预算启动新引擎检查；检查期间来了"用户在等"的请求，就中止检查（不算失败），重启旧引擎来服务（期间发进度事件），检查推到下一次安静时刻。只有新旧两份都在装得下的公式之内时，才允许旧组合边服务边检查。因内存不够被拒绝的检查不算失败。
- 依据：每个任务旁边一句大白话的质量结论，例如"在 40 条测试上全部正确"，点开看评测集条数、硬性条目数、评测日期和引擎包版本；速度一律用本机实测，不写实验室芯片上的速度。

## 8. 安装、更新与卸载

**安装**（ADR 0002）
- v1 发主控 DMG。每个配件的下载按钮给的都是同一个主控 .app，放在以配件命名的 DMG 里，.app 本身的名字是"安装<配件名>.app"（例如"安装螺壳输入法.app"），不和配件自己的 .app 同名；图标统一，按配件定制在 v1.x。
- **首次运行**：
  1. 按自己的文件名记下要预选的配件。
  2. 如果 `~/Applications/螺壳主控.app` 已经装着，就把要预选的配件交给已装的主控（例如通过 URL scheme），由它做预检和征求同意，自己随即退出，不覆盖已装的主控。已装主控的配方里没有这个配件时，它说明"需要先更新螺壳主控"，用户同意后立即自更新（这次不等安静时刻，但仍先等"用户在等"的请求跑完），更新后接着预检。
  3. 否则，如果发现自己在 DMG 里、被 App Translocation、或者不在规范位置，就把自己拷到 `~/Applications/螺壳主控.app`、去掉 quarantine 标记，从那里重启；原来那份在可写位置时才删掉。
  4. 预检硬件档、磁盘、macOS 版本（低于引擎包要求的就停下；v1 是 26.2，2026-10-15 定）和主要任务状态。
  5. 用一屏说清要装的配件、引擎包、模型和合计大小、预计下载时间，用户点一次就全部同意。
  6. 注册登录项。
  主要任务在这台 Mac 上不支持时，在下载任何模型之前停下说明；用户选择不装，而且这次是新装主控、没有别的在装配件时，就连主控一起撤掉。
- **按用户安装**：所有东西装在当前账户下，不要管理员权限，不装特权程序（ADR 0007）。同一台 Mac 的多个账户各自独立。
- **登录项**：只有主控有。常驻配件（通过 `PUT /accessory/resident` 声明）由主控在登录时经 `NSWorkspace.openApplication` 启动（这样辅助功能等系统权限算在配件自己头上），异常退出就重启（判定见 §4 `POST /accessory/exiting`）；其余配件由用户自己打开。配件删掉自己原来的登录项。

**更新**
- **发布车**（ADR 0009）：主控自更新（Sparkle 一类）；更新后在安静时刻按发布清单安装：
  1. 下载新引擎包，对新组合做首次冒烟检查（§7），此时不切换，旧组合继续服务；
  2. 安装配件（请配件退出、原子替换、重启）——新配件版本在"上一版"组合上也已验证，可以先跑在旧组合上；
  3. 发布清单里的配件全部装好后，才切到新组合。
  冒烟不通过就不切换，配件照装。配件持有未失效的预热租约（界面开着）时不替换它，推到租约失效之后的下一个安静时刻。下载时校验签名身份和哈希。下载任何模型都要先问。
- **渠道和发布仓库**（10-28，luoke-core#36；ADR 0002 修订）：主控按自己装的那一版认渠道，只查本渠道。beta 和正式版发在 `luokelabs/luoke-releases`，内部版发在单独的 `luokelabs/luoke-internal-builds`（都公开，检查更新不带令牌）；外部的人从发布列表里就碰不到内部版。
- **撤回清单**：随检查更新一并取回，取到就立即停用，不需要先装新版本；检查更新不受自动更新开关影响。需要核实所用更新框架是否给更新源本身签名；如果没有，撤回清单另用更新签名私钥签名（§13 第 7 项）。更新源要保证国内能访问，否则撤回送不到。
- **自动更新开关**：用户可以关掉自动安装，开关只管要不要安装新版本；关掉后有新版本时由主控提示。
- **回退**：
  - **引擎包**：任何一次冒烟检查失败（首次，或 macOS 更新后补做的）或熔断，这个引擎包立即停止服务。上一版引擎包在当前系统上冒烟通过、且在装配件在它的组合上已验证，就退回它（主控保留上一版引擎的适配器，主控本身不回退）；否则相关任务"暂停中"（macOS 更新后失败的附"等待适配新系统"；首次安装、没有上一版可退的附"本机检查未通过"，状态灯说明原因并提示导出诊断信息，配件照常安装以便显示这个状态）。留在上一版的机器，照装发布里在上一版组合上已验证的配件版本，其余配件保持已装版本；每次新发布、每次 macOS 变化时重试一次现役引擎包的首次冒烟检查。
  - **配件**：新版本报告正常（§4）之前异常退出两次（崩溃，或者不是经 `POST /accessory/exiting` 的退出），就退回旧包；旧包保留到报告正常为止。退回的旧版本只在"上一版"组合上已验证时，引擎包一并退回上一版。配件在迁移自己的数据库之前，把快照放在约定位置（配件数据目录下的 `.luoke-snapshot/`，附上做快照前的配件版本）；回退时由主控在启动旧包之前把快照拷回。快照包含配件启动时可能迁移的所有数据库（由配件在接入契约里声明，§11）。报告正常之后不再退回配件。
  - **常设规则**：任何时候，在装配件版本在所用组合上不是已验证版本，相关任务都"暂停中（等待配件更新）"。

**换代**（v1.x）
- 换底座或专用模型。前提：每个配件都有在新组合上已验证的版本；"更新配件"和"下载新模型"放在同一次征求同意里。
- 切换：小内存档上先等旧底座闲置卸载、确认内存回收，再加载新底座做首次冒烟检查；正在跑的后台请求在旧底座上跑完。
- 旧组合保留到新组合稳定运行一段时间之后（例如累计开机 14 天），冒烟失败或熔断时自动回退。
- **维持期**（是否保留、定多长待定）：用户拒绝或推迟换代后，旧底座以"维持中"的角色继续受支持（暂定 6 个月）；期间新配件版本要在新旧两个组合上都验证；只有新底座才有的任务显示"需要换代"。期满后转为"已退役"：已装的版本照常能用，不再收到新版本。

**撤回**
- 撤回清单列出要停用的模型文件哈希和引擎包版本。主控取到后立即停用，不需要征得同意，并由状态灯和受影响的配件说明原因；有在装配件已在其上验证过的旧组合就回退过去，否则相关任务"暂停中（等待替换）"。文件不自动删除，因许可原因撤回的才删并告知用户。
- v1 里底座或专用模型被撤回时，由下一次发布车带上替换的模型（作为新的现役组合，配件新版本都在它上面验证）。替换按新装处理：任务状态从"暂停中（等待替换）"转为"需下载"，用户同意后下载，首次冒烟检查通过即启用，不走换代流程。这是 v1 唯一会换模型的情况。
- v1 撤回随检查更新取回，同时在社区公告；v1.x 随配方独立通道送达。

**换机**
- 主控记录机型标识（`hw.model`）和芯片，与上次不同就视为换机：清掉本机实测速度，看门狗退回配方给的保守默认值，对所有在用组合重做首次冒烟检查（§7）；内存档也不同时，再提示下载新硬件档的底座（征得同意），并把不再适用的旧底座列为可释放。

**卸载与回收**
- **按引用回收**：主控的存储页列出不再被任何在装配件的任务用到的模型（"可释放 N GB"，说明原来谁在用），用户点了才删；卸载配件时顺带询问。
- **卸载配件**：默认保留它的用户数据，用户勾选"同时删除我的数据"并看过清单后才删，每个配件只删它在接入契约里声明的数据（§11）。记忆不在其中：`~/.luoke/mem.db` 归用户、由 luoke-mem 管（顶层 ADR 0014），卸载任何配件都不删记忆；卸载对话框另有一个默认不勾的选项，勾了由主控请 luoke-mem 执行（与 luoke-mem 2026-10-10 商定，见 luoke-mem DESIGN「整份记忆」）：在删配件文件之前，主控用**主控 .app 自带的 Python 和打在里面的 luoke_mem** 跑 `python3 -m luoke_mem forget-tool <配件标识> --dry-run`（绝不用配件的引擎文件夹这类可替换内容里的代码，它们只该在沙盒里跑，也不用 `/usr/bin/python3`，没装命令行工具时它会弹安装窗口），拿到 `{"tool", "records", "notes"}` 的条数，选项文字写成"同时从记忆里忘掉<配件名>写的 N 条记录和 M 条理解"（条数为 0 就不显示）；勾了就去掉 `--dry-run` 再跑一次。退出码 1（记忆文件比这份 luoke_mem 新、打不开）时只提示、不阻止卸载。忘掉的范围由 luoke-mem 定：它写的记录、它形成的理解，以及别的工具只靠它的记录形成的理解。
- **记忆不单独卸载**：它打在主控里（顶层 ADR 0014），「卸载全部」删主控时也不删 `~/.luoke/mem.db`；主控不另给"清空整份记忆"的选项（清空在记忆界面里做）。早期单独装的 `~/Applications/螺壳记忆.app` 在升级时迁进 `previous.noindex` 并注销登记。
- **记忆随主控更新**：主控升级就是记忆升级。升级前请主控 .app 里跑着的记忆进程退出（界面服务、learn），再换 .app。
- **直接拖进废纸篓**：配件没有自己的登录项，不会留下孤立的后台项目。v1 主控在自己启动时、登录时拉起常驻配件失败时、以及打开存储页时核对已装配件是否还在；发现不见了，就提示"它的数据还在，位置在哪"，并把它的模型列为可释放。每日核对在 v1.x。

## 9. 用户界面与沟通

- **谁来说**：和某条请求有关的提示，由配件在用户正在看的地方显示；只有整机的事，主控才通过状态灯和通知说（下载同意、有新版本、撤回；磁盘紧张提醒在 v1.x）。在"用户在等"的路径上，主控和配件都不弹抢焦点的窗口（用户在备忘录里打字时，弹出的对话框会接住后面打的字）。
- **状态灯**：当前底座、正在做什么、功耗档、全机后台状态。
- **任务状态**：
  - 可用（可附"在这台 Mac 上较慢"）；
  - 需下载；
  - 下载中（附进度和子原因，例如等网络、正在检查）；
  - 暂停中（整个任务暂时做不了，例如撤回待替换、熔断、等待适配新系统、本机检查未通过、等待配件更新）；
  - 需要换代（v1.x）；
  - 不支持（这台 Mac 上长期如此，附原因，同 §4 原因码 `unsupported`）。
  按任务报告，所以配件可以部分可用。用电池、低电量这类只影响后台的情况，走全机后台状态，不改任务状态。
- **依据**：质量结论一句大白话，点开看评测集条数、硬性条目数、评测日期和引擎包版本；速度用本机实测。也是"不支持"原因的出处。评测集本身不公开。
- **说明要充分**：凡是涉及下载、占用内存、删除、回退的地方，都说清大小、原因和用户能做的事。
- **界面不说废话**：avoid unnecessary secondary labels and descriptions. let the layout do the explaining. 副标题、旁注、解释性小字能省就省；上一条的大小、原因只在用户要做决定的那一步写，一句话。

## 10. 安全、日志和数据边界

边界只有一条：数据不出用户自己的设备；本机组件之间不为隐私设限（顶层 ADR 0013）。下面的规则不是为了"少看数据"，各有自己的理由。

**请求文字只留在内存里**（理由：日志和缓存不是存内容的地方，内容的正本在各工具和记忆里；诊断会出本机，必须只含元数据；oMLX 的 SSD 缓存实测命中 0%，关掉不亏，见 §5。以后要做提示缓存或回放时再放开）
- 请求文字及其派生物（token、KV、输出）不落盘：oMLX 按 §5 的启动清单运行（包括固定的日志级别），mlx-lm 工作进程同样不落盘。
- 主控日志只记元数据：任务、配件、组合和配方版本、token 数、耗时、结束原因、错误类别。异常和崩溃报告统一经过去内容过滤。
- 用带标记字符串的请求做测试（生成请求和打分请求都要），除了正常完成，还必须覆盖：格式不合法、超长输入、被打断或断开、内存保护拒绝、引擎内部异常；确认主控日志、`{base_path}/logs`（含 `crash.log`）、缓存目录、工作进程的输出和崩溃报告里都找不到这个标记。测试不通过的引擎包版本不得写进配方。

**不回传数据**
- 默认不向外上报任何东西。v1 只做"导出诊断信息"：机型、芯片、内存、硬件档、各组件版本、任务状态、冒烟检查结果和本机速度、错误码、引擎崩溃摘要；绝不含请求文字及其哈希（短文本的哈希能被字典穷举）。用户看过后自己决定是否发给社区。
- 自动上报推到以后；在那之前可以给社区发一个独立的测速脚本。
- 检查更新必然要联网，只带取更新所必需的信息。

**本机边界**
- 任务层只开在本账户的 socket 上，配件标识只用于识别，不是安全措施。唯一的 TCP 入口是给高级用户的本机端点（默认关；V1 §2b，顶层 ADR 0014 修订）：只听 127.0.0.1、带密钥、校验 Host、拒绝带 Origin 的请求。
- 引擎这一跳：oMLX 只听 127.0.0.1 的随机端口，每次启动配一个随机密钥；发出请求和密钥之前，先按 PID 核对监听这个端口的是自己拉起的子进程。
- **孤儿进程**：主控在主控环境里用 PID 文件（含进程启动时间）记下自己拉起的引擎进程；启动时先结束上次遗留的引擎进程、确认内存回收，再拉新的。mlx-lm 工作进程由主控的代码控制，发现父进程消失就自行退出。
- **配件自己的本机网页**（如有）是配件接入契约的一部分（§11）：只听 127.0.0.1，每次启动生成随机 token，每个接口都校验 token 和 Host 头，防止网页借 DNS rebinding 访问。
- 用户环境：看进程列表；复用本机已有的模型时只读、只克隆用户引擎的模型文件（`~/.omlx/models`、Hugging Face 缓存、LM Studio，按文件哈希核对、APFS 克隆，V1 §6），不改用户引擎的文件和设置，不读它们的凭据；不碰受 TCC 保护的文件夹。
- **签名**：主控、配件、引擎包都用同一个 Team ID 签名，开启 hardened runtime 并公证；更新前比对新旧包的签名身份。主控下载的文件没有 quarantine 标记，Gatekeeper 不检查它们，主控自己的签名与哈希校验是唯一的关。
- **密钥保管**：Developer ID 证书私钥、更新签名私钥、v1.x 的配方签名私钥，都不放成普通文件。配方签名用 P-256，私钥放在硬件密钥或 Secure Enclave 里；更新签名若用 Sparkle 一类的 Ed25519（Secure Enclave 不支持），私钥放在硬件密钥或每次使用都要 Touch ID 的钥匙串条目里。发布脚本签名前要负责人确认一次指纹；AI 代理的会话不得读取这些密钥。
- **配件转来的用户输入**（例如输入法看到的打字内容）经过主控本来就没问题（都在本机，顶层 ADR 0013）。主控对这类内容的做法同上：只走 socket（或用户自己开的本机端点）、只在内存、不进日志和诊断信息——理由是日志和诊断不是存内容的地方，诊断还会出本机。

## 11. 配件接入契约

每个配件都必须满足下面这些条件，主控只按这份契约对待配件，不为任何具体配件做特殊处理。现有配件各自要做的改动见 [docs/research/accessory-requirements.md](research/accessory-requirements.md)。

**打包与身份**
- 每个配件的 .app 里带一份配件清单 `Contents/Resources/luoke-accessory.json`（配件标识、bundle id、名字、版本、类型、入口、是否常驻、是否读写记忆、任务列表、数据位置、组件配件的命令行），主控安装、卸载、核对任务归属都读它；字段以 V1 §8 为准（2026-10-12 冻结）。
- 签名公证的 .app，和主控同一个 Team ID，开启 hardened runtime。安装路径由配件类型决定（应用在 `~/Applications`，输入法在 `~/Library/Input Methods`），已发布配件的 bundle id、Team ID 和安装路径不能变（变了会丢辅助功能等系统授权）。
- 用 Python 写的部分自带一份 Python（ADR 0010），不依赖 `/usr/bin/python3`；尽量只用标准库，确实需要第三方包时随 .app 签名打包、版本固定。
- 不注册自己的登录项。需要开机运行的，通过 `PUT /accessory/resident` 声明，由主控启动和保活；正常退出前调用 `POST /accessory/exiting`。
- **组件配件**（现在只有 luoke-mem）：代码（`luoke_mem`）打进主控自带的 Python，清单放在主控 .app 的 `Contents/Resources/memory/`，不单独装、不单独签（顶层 ADR 0014；V1 §6）。不常驻，不声明数据；后台的模型任务像其他配件一样在清单里声明、交评测集、进配方，登记成空闲任务由主控在安静时刻拉起（顶层 ADR 0014、0015；V1 §8）；清单里声明卸载用的命令行（`forget-tool`）。读写记忆的配件现在各自带一份 luoke_mem 库（放在它自己的 .app 里，或者像输入法那样放在沙盒组件自己的文件夹里），发布时核对和钉住的 luoke-mem 一致；改成直接用主控里那份由 luoke-mem 牵头、四方商定（顶层 docs/review-2026-10-19.md）。打开记忆界面：`luoke://memory`（可带 `?note=`、`?view=recent`），由主控接住。 **系统拉起的配件**（例如输入法，由 macOS 的输入源机制启动和重启）例外：不声明常驻，主控不计它的异常退出；装好后由主控引导用户完成系统侧的启用（例如到系统设置添加输入源）。

**用模型的方式**
- 只通过任务层用模型，每次请求在请求头里自报标识和版本；不点名模型，不提供选模型的界面。
- 不在自己的代码里写死任何随模型变化的常数（以 token 或 nats 为单位的门槛、上限、奖励等），全部从 `GET /tasks` 给的任务参数读；按字符上限截短输入，按批大小分批，在请求里报条目数。
- 生成请求一律流式；处理全部原因码（§4），按 `retry_after` 重试；收到终止事件 `luoke.error` 就丢弃已收到的部分输出。
- 请求等级："用户在等"只用于有人正盯着结果的单次请求；批量工作标"后台"；`allow_battery` 只用于用户亲手启动的批量工作。
- 交互将要开始时（例如界面打开时）可以发起预热，需要期间续期。

**质量**
- 每个任务交评测集：录好的完整请求（多步任务是自带的评测程序）、判分规则和及格线；标明主要任务和可选任务。对速度敏感的任务声明延迟要求：实验室关卡的机器、口径、数值，以及给用户机器用的本机阈值。

**数据与升级**
- 声明自己的数据位置（目录、钥匙串条目），用于卸载时的数据清单；每个配件只删自己声明的数据。
- 启动时如果要迁移数据，先把所有可能迁移的数据库快照到约定位置（数据目录下的 `.luoke-snapshot/`，附做快照前的版本）；完成迁移后调用 `POST /accessory/ready` 报告正常。

**界面与安全**
- 和某条请求有关的提示在自己的界面就地显示；在"用户在等"的路径上不弹抢焦点的窗口（§9）。主控不可用时暂停相关功能，并就地说明。
- 自己的本机网页（如有）只听 127.0.0.1，每次启动生成随机 token，每个接口都校验 token 和 Host 头。

## 12. 实现事项（不需要产品决定）

括号里注明分期，未注明的属于 v1。

- **下载**：分块下载、支持续传，先写临时位置，哈希校验通过后原子改名；下载前检查磁盘（保留的上一版也算进去）；网络是计费或受限的（`NWPath` 的 expensive / constrained）时不自动下载（只管首次运行以后的自动补下：提示、等用户点「重试」；用户自己点的下载照下）。
- **加载安全**：模型文件夹里出现清单外的文件就拒绝；加载时一律 `trust_remote_code=False`。
- **熔断**：崩溃和打断分开计数；主控只在还没向配件发出任何输出时自动重试一次，已经发出输出的请求返回 `engine_failed`，由配件决定是否重发；看门狗按本机实测速度设首 token 和 token 间隔超时，还没有本机实测时用配方给每个组合的保守默认超时；短时间内反复崩溃就熔断，相关任务"暂停中"，并作为引擎包回退的依据。oMLX 内存保护的拒绝、驱逐和全部中止按"内存不够"处理（§5），只有内存压力正常时仍反复全部中止，才计入熔断。
- **主控重启和自更新**：v1 主控重启即重启引擎，按 §10 清理孤儿进程；自更新前先停收新请求，等"用户在等"的请求跑完，后台请求返回 `interrupted`，只在安静时刻更新。撤回清单的生效不等自更新（§8）。
- **睡眠与时钟**：后台工作不阻止系统睡眠，只在接电源且有"用户在等"的请求进行时短暂持有防睡眠断言；收到即将睡眠的通知时，后台请求按打断处理；dark wake 期间不用 GPU；拔掉电源后不接新的后台请求（带 `allow_battery` 或任务标了"用电池也做"的除外，见 §6）；计时一律用单调时钟或开机时长。
- **系统更新与换机**：记录 macOS 的 build 号和机型标识，任一变化就补做冒烟检查、重算 GPU 预算（换机按 §8 处理）；引擎包清单注明支持的 macOS 范围（oMLX 可能按系统版本分别出包），超出时相关任务"暂停中（等待适配新系统）"。
- **其他**：模型和引擎用 `tmutil addexclusion` 排除出时间机器备份；用 `SMAppService.status` 检测主控的登录项有没有被用户关掉，在配件界面提示。
- （v1.x）每日核对配件是否还在、磁盘紧张提醒；迁移助理带走配件系统授权的实测。
