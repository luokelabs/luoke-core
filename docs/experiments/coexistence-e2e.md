# 端到端共存实测：16 GB 上交互打分和后台批量能不能共存（经主控）

- **对应**：[V1.md](../V1.md) 开头"要验证的三件事"第二件；实测 0（[coexistence.md](coexistence.md)）给出的共存规则在主控里落地后的验证。
- **机器**：16 GB 测试机（Mac mini M1 16 GB），macOS 26.2，无人登录图形会话（全部经 ssh）。主控开发版（`luoke_core`，实验室构建，socket `/tmp/luoke-hub-16.sock`，16 GB 档：天花板 10 GB，底座 Qwen3.5-9B-4bit 不常驻，打分模型 Qwen3.5-0.8B-Base-4bit）。
- **负载**：
  - 打字：luoke-ime 的 `engines/xiaohe/bench.py`（它扮演壳：经引擎协议逐键喂小鹤引擎，个人化组件的打分转给主控，按 `GET /tasks` 的批大小分批），中文博客语料 600 条（不公开），120 ms 一个键，`--scorer hub`。语料只在 16 GB 测试机临时目录用，跑完删。
  - 后台：luoke-mail 的 `bench/background_load.py`（和 .app 里同一套代码：示例收件箱 44 封分拣、示例归档清理、示例订阅阅读补到 6000 字；标 background，busy / interrupted / not_ready 按 `retry_after` 等，paused 不等）。
  - 主控状态时间线：`tools/hub_status_log.py` 每秒记 `/status`。
- **日期**：2026-10-13。三轮，前两轮各发现一个主控的问题（见 §3），第三轮是干净的。

## 1. 结果

| 段 | 条件 | 主控里每次打分 p50 / p90 | 最后一个键到最终答复 p50 / p90 | 首选准确率 | 后台 |
|---|---|---|---|---|---|
| A 打字单跑 | 底座未加载 | 84 / 135 ms（7246 次，命中 100%，无拒绝） | 367 / 546 ms | 不标 more 的 90.3%，最终 89.8% | — |
| B 后台单跑 | 安静时刻 | — | — | — | 分拣 44/44 完成，每封约 50 s；清理 6/17、订阅阅读 4/12（其余在均衡档的间歇里等）；整轮 53 min |
| C 后台跑着时打字 | 底座已加载、分拣在跑 | 72 / 122 ms（8313 次，命中 100%，无拒绝）；底座仍在内存里时的 3 次 p90 154 ms | 300 / 471 ms | 同 A | 打字期间一条后台都没接；打字结束后恢复 |
| L 对照：本机打分进程，不经主控 | 同 A 的回放 | （本机进程，不经 socket） | 319 / 492 ms | 不标 more 的 90.5%，最终 89.8% | — |

- **底座让路**：C 段第一次打分到达的同一秒（18:23:58）底座卸掉；之后的 8310 次打分和单跑一样快。
- **后台不进来**：打字期间（交互中 60 s 窗口 + 打分后 3 分钟窗口）主控对后台一律 `busy`，luoke-mail 的脚本按 `retry_after` 等，没有报错；打字停下后按安静时刻的规则恢复。
- **socket 的开销**：往返比主控里的用时只多 3 ms（p50 2.8、p90 3.8 ms）。M1 上每次打分 80 多毫秒几乎全是 0.8B 打分本身。
- **经主控 vs 本机打分进程**（同一语料、同一回放、都不经 Swift 壳）：最后一个键到最终答复 p50 / p90，经主控 367 / 546（A）和 300 / 471（C），本机 319 / 492（L）——差别在两次经主控之间的波动之内，准确率一样。M1 上两条路都是 p90 约 500 ms，远超输入法注册页"约 150 ms 内"（那是基础款 M4 上量的）：这是 M1 的能力，不是主控这条路造成的。开发机（M5 Max）上 luoke-ime 量到经壳走主控比本机多 15–25 ms（102 对 77），其中约 19 ms 在不经壳的 bench 里就有，壳本身约 6 ms。
- **"较慢"标记**：A 段后主控给 `luoke-ime.rerank` 标了 `slow {measured_ms: 152, threshold_ms: 124}`——M1 上经主控的单次打分超过输入法给的本机阈值，是否用由输入法定（配件决定），标记本身工作正常。

## 2. 结论

16 GB 上可以共存，靠的是规则而不是算力：底座只在安静时刻加载、用户一打字就卸（同一秒）、打字期间不接后台；用户回来的代价是第一个键约 1 s。代价是后台只能在安静时刻慢慢做（分拣每封 50 s、均衡档再歇等长时间），以及打字本身在 M1 上就比阈值慢——经主控和本机打分进程一样慢（p90 约 500 ms 对 150 ms 的要求），主控只多 3 ms 的 socket 往返。两件事都是 16 GB / M1 的真实能力，不是主控的问题；写进依据让用户看得见，输入法按 `slow` 标记决定用不用。

## 3. 过程中修掉的两个主控问题

1. **预热租约拦住了让路**（第一轮）：hub_smoke 留下的 600 s 预热租约让底座在打字期间多留了 5 分钟，机器换页、后台因"等内存"暂停。改成 16 GB 档上用户一打字底座立刻卸，租约也拦不住（V1 §3 驻留）。
2. **用换页增量判内存压力会把自己暂停掉**（第二轮）：16 GB 上主控自己加载底座就换出几 GB，采样线程据此判成 warn，后台刚被接纳就被打断、全机后台暂停 3 分钟。改成看内核的压力等级（`kern.memorystatus_vm_pressure_level`），且 16 GB 档上底座在内存里时 warn 不算数，只有 critical 才动（V1 §3 内存）。

3. **加载过程中的 warn 也是自己造成的**（第三轮 C 段之后）：打字停下 5 分钟后后台被接纳、底座开始加载，加载那几秒内核压力到 warn，而主控此时还没把底座记成"已加载"，于是又判成别人在挤、全机后台暂停 3 分钟，恢复晚了 4 分钟（18:49 接纳、18:53 才真正开工）。改成"正在加载"也算自己的。

另外一处口径：主控的"装得下"机器检查给 16 GB 档不留 1 GB 余量（本来就是挤着用、用完就卸），否则 M1 上刚打完字系统 wired 5.8 GB 时 5.8 GB 的底座会被拒。

## 4. 没测到的

- ~~打字打断一条正在跑的后台请求~~ 用 `tools/interrupt_probe.py` 补测了（安静时刻发一条 5930 字的订阅阅读，后台跑起来 10 s 后发一次打分）：打分到达时后台正在加载底座，后台当场收到 `interrupted`（它这条活了 4.4 s），底座在打分后 1.1 s 卸掉；那一次打分本身花了 1.1 s（M1 的 GPU 正被底座加载占着），之后恢复正常。这就是 16 GB 上"用户回来"的代价：第一个键约 1 s，而不是实测 0 里按 prefill 块算的 6–11 s——主控在第一次打分就切，不等 prefill 块结束。还没测到的只剩正在 prefill 中段（8k 要 100 s）被切的情形，按设计最多多等一个块。
- 经 Swift 壳的端到端：16 GB 测试机没装输入法 .app；壳那一跳按 128 GB 开发机上的数约 6 ms。
- 冒烟检查在 16 GB 上的真实首次（这次用的是缓存的通过记录）。

## 5. 补测：慢的机器少给一半候选（2026-10-13 晚）

- **对应**：luoke-ime 注册页「慢的机器」（2026-10-13 定：主控给 `luoke-ime.rerank` 标 `slow`，输入法每一步少给模型一半候选）。luoke-ime d488e3b 做完后请主控在 16 GB 测试机上量 full 和 small。
- **做法**：同一台 16 GB 测试机、同一语料 600 条、逐键 120 ms、`--scorer hub`，主控实验室实例（底座未加载，只有打分模型），`engines/xiaohe/bench.py --engine-option budget=full|small --hub-dump`，各跑一遍（full 21:20–21:44，small 21:44–22:06）。budget 直接给，不看 `slow` 标记。

| | full（苹果 12 / 单字 4 / RIME 8） | small（6 / 2 / 4） |
|---|---|---|
| 最终首选 | 89.8% | 88.8% |
| 不标 more 的首选 | 90.2% | 88.8% |
| 最后一个键到不标 more 的答复 p50 / p90 / p99 | 364 / 539 / 719 ms | 260 / 364 / 430 ms |
| 最后一个键到第一份答复 p50 / p90 | 74 / 165 ms | 56 / 104 ms |
| 停顿 0 / 100 / 200 ms 后按空格：不必再等的（壳最多再等 150 ms） | 5.5% / 28.0% / 46.7% | 17.8% / 47.0% / 85.0% |
| 同上：上屏的首选准确率 | 70.5% / 80.0% / 82.0% | 80.3% / 82.5% / 87.0% |
| 主控打分请求数；每请求候选均值 | 7221；10.2 | 8482；5.1 |
| 主控里每次打分 p50 / p90 / p99 | 84 / 137 / 211 ms | 66 / 82 / 133 ms |
| 往返比主控里多 | ≈ 3 ms | ≈ 3 ms |

前缀缓存命中都是 100%，没有拒绝。

- **减半在 M1 上的代价和收益**：首选 −1.0 点（M5 Max 上 luoke-ime 量到的也是 −1.0），最后一个键到选好 p90 539 → 364 ms；停顿 200 ms 再按空格，不必再等的从 47% 到 85%，上屏的首选准确率 82% → 87%（比 full 还高：更多次等到了重排结果）。
- **每次打分的时间里固定部分占大头**：候选 10 → 5，主控里 p50 只从 84 降到 66 ms；p90 137 → 82 是尾巴缩短了（请求短了，被下一个键打断、排队的少——small 完成的请求反而多，8482 对 7221）。再减到 4 / 1 / 2，每次最多再省十几毫秒，收益递减。要赶上"最后一个键后 150 ms"，省的得是最后一个键之后串行的轮数（p50 260 ms ≈ 4 次 66 ms）：比如只重排最后几个词、或最后一个键后只做一轮。
- **给 luoke-ime**：减半值得（1 点准确率换来按空格时多数时候不用等）；再往下减候选不如减轮数，要不要再减由 luoke-ime 定。

## 6. 补测：慢的机器上少算几步（2026-10-14 凌晨）

- **对应**：定下的下一步（luoke-ime 注册页「慢的机器」）：标了 slow 的机器上不再减候选，只减最后一个键之后接连的轮数，并且模型算着时先答新键的快候选（luoke-ime d591926）。
- **做法**：同 §5（16 GB 测试机、同一语料 600 条、逐键 120 ms、经主控、底座未加载），都用 `budget=small`：r2 = 现在的 small（最多 2 步 + 先答新键），r0 = 不限步数（和 §5 的 small 只差先答新键），r1 = 最多 1 步。

| | §5 的 small（旧） | r0 不限步数 + 先答新键 | r2 最多 2 步（现在的 small） | r1 最多 1 步 |
|---|---|---|---|---|
| 最终首选 | 88.8% | 88.8% | 88.8% | 88.8% |
| 不标 more 的首选 | 88.8% | 89.0% | 88.2% | 87.0% |
| 最后一个键到不标 more 的答复 p50 / p90 / p99 | 260 / 364 / 430 ms | 187 / 270 / 319 ms | 150 / 183 / 233 ms | 105 / 136 / 188 ms |
| 最后一个键到第一份答复 p50 / p90 | 56 / 104 ms | 25 / 32 ms | 25 / 32 ms | 28 / 35 ms |
| 停顿 0 ms 按空格：不必再等的 / 上屏首选 | 17.8% / 80.3% | 30.5% / 81.7% | 49.7% / 83.5% | 95.3% / 86.8% |
| 停顿 100 ms 按空格 | 47.0% / 82.5% | 83.5% / 87.5% | 99.3% / 88.0% | 99.7% / 87.0% |
| 停顿 200 ms 按空格 | 85.0% / 87.0% | 100% / 89.0% | 100% / 88.2% | 99.8% / 87.0% |
| 主控打分请求数；主控里 p50 / p90 | 8482；66 / 82 ms | 10831；56 / 66 ms | 10719；56 / 67 ms | 7281；61 / 78 ms |

前缀缓存命中都是 100%，没有拒绝。

- **先答新键**本身就值：r0 对比旧 small，最终首选不变，第一份答复 p90 104 → 32 ms，选好 p90 364 → 270 ms。
- **限 2 步**（现在的 small）再把选好的 p50 / p90 压到 150 / 183 ms：停顿 100 ms 再按空格 99.3% 不用等、上屏首选 88.0%（旧 small 82.5%）；代价是"不标 more 的首选"从 89.0% 到 88.2%，最终首选不变。M1 上 p50 正好到输入法注册页的"约 150 ms 内"。
- **限 1 步**更快（105 / 136 ms，停顿 0 ms 也 95% 不用等），但不标 more 的首选再掉到 87.0%，停顿 100 ms 时上屏首选 87.0%，比 2 步低 1 点。要不要用由 luoke-ime 定。
- **原始数据**：16 GB 测试机 `~/luoke-coexist/results/rounds/`（r2 / r0 / r1 的 .txt、hub-dump .jsonl、`--result` 证据 JSON，不含文字）；语料已删、主控实例已停。
