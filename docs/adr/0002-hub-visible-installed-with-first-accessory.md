# 主控对用户可见，随第一个配件一起装上

luoke-core 不做成配件里看不见的库或框架，而是做成用户看得见、会打开的主控：菜单栏常驻状态灯，用户在这里看到这台 Mac 能跑什么、在用哪个模型、谁在用、功耗档，并对下载和换代表示同意。但用户不必先知道它：它随第一个配件的安装一起装上。理由是共享的资源（几十 GB 的下载和内存、风扇和电量）必须让用户知情和同意，藏在某个配件里会让用户困惑"为什么邮件助手占了 30 GB"；也给螺壳一个"家"。

## Considered Options

- **看不见的底座（库 / 框架）**：用户只看到各个配件"自己能用"。否决：资源占用和同意无处安放；每个配件都得各自解释下载和占用。
- **先装主控、再在主控里挑配件（商店式）**：否决，用户不该先学会"主控是什么"才能用上第一个配件。

## 修订（2026-10-09，设计审查后）

第一版的落地方式：每个配件的下载按钮给的都是同一个主控 .app，放在以配件命名的 DMG 里，.app 本身叫"安装<配件名>.app"（不和配件自己的 .app 同名）。首次运行时按自己的文件名预选配件，把自己拷到固定位置 `~/Applications/螺壳主控.app` 并从那里重启，然后预检、用一屏说清全部下载、一次同意。按配件定制图标在 v1.x。"随第一个配件装上、用户不必先知道主控"不变。

主控已经装着时再运行某个配件的安装器，它不覆盖已装的主控，而是把要预选的配件交给已装的主控，由后者预检和征求同意（DESIGN §8）。

## 修订（2026-10-24，装进 /Applications）

主控本体的固定位置从 `~/Applications/螺壳主控.app` 改为 `/Applications/螺壳.app`（改名见负责人 10-23，位置见 ADR 0012）：主控 DMG 里拖进「应用程序」；应用的安装器（`安装<配件名>.app`）照旧双击就装，把主控拷到 /Applications，写不进去就退回 `~/Applications`。已装的两处都认，以实际位置为准。

## 修订（2026-10-26，发布只出螺壳一个包）

负责人 10-26 定（luoke#7："对用户来说就是装一个螺壳，可以在里面开启不同的应用"）：发布页只放螺壳的 DMG，不再出按应用命名的安装器 DMG（`install-<应用>-*.dmg`）；邮件助手、输入法都在螺壳的「应用」窗口里装和升级，应用的 zip 照旧在发布清单里供螺壳下载。螺壳里认"安装<应用>.app"的代码留着，以前发过的安装器打开照样能用；`release.py --installer-dmgs` 还能出，备用。

## 修订（2026-10-28，内部版换单独的仓库）

负责人 10-28 定（luoke-core#36）：内部版不再发在 `luokelabs/luoke-releases`，改发到单独的公开仓库 `luokelabs/luoke-internal-builds`；luoke-releases 只留 beta 和以后的正式版。

理由：GitHub 同一个仓库的发布列表谁看都一样，内部版一天两版，把 beta 挤到下面；外部的人从官网点进列表很容易装错内部版，而主控按装的那一版认渠道，装了内部版就一直跟内部版。官网的下载按钮链的是 `releases/latest`，内部版是 Pre-release，不受影响，受影响的只是翻列表的人。新仓库也得公开：主控检查更新不带令牌。

做法：流水线按发布号选仓库；主控按渠道选仓库，查更新时翻页（原来只看最新 40 条，beta 迟早会被挤出第一页）。过渡：internal-1028 及更早的主控只在 luoke-releases 里找内部版，所以改完后的第一版内部版在 luoke-releases 也建一条同名的 Pre-release，只放 `release.json`（清单里的地址都指向新仓库），旧版据此升级过去；之后只发新仓库。luoke-releases 里旧的内部版先不删。外部的人已经装了内部版的，过渡版会把他们带到新仓库，仍在内部版渠道；要回 beta 得自己从官网重装。
