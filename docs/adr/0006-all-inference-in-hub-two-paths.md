# 推理全部在主控环境里：共享模型走派发，专用模型直连

所有模型（包括只为某个配件服务的专用模型）都在主控环境里运行、由主控加载、卸载、计内存和施加功耗规则；区别只在请求的路径：对共享模型（底座）的请求经过派发（排队、两级等级、打断），对专用模型的请求不经派发、直接交给它。理由：共享大模型是全机最稀缺的资源，必须有一处排队；专用模型只有一个使用者，绕一层派发只增加延迟。最初设想让 jiu 在自己进程里跑模型，但核实发现 jiu 本来就隔着两层子进程推理（Swift → Python 3.9 → oMLX 的 Python 3.11），多经主控一跳是亚毫秒级；而"打的字不交给主控"在本机 AI 里不构成约束。

## Considered Options

- **所有请求都经派发**：否决，jiu 的几十毫秒打分承受不起排队。
- **主控只管控制、不碰请求，配件自己连引擎或在自己进程里跑**：否决，共享模型无人仲裁，GPU 争抢也无人协调。

## Consequences

- 专用模型最近几秒有请求时，主控视为用户正在交互，派发不启动新的后台请求——只有两边都在主控手里才做得到。
- 请求文字会经过主控进程，因此主控必须守住"不落盘、不显示、不进日志"的纪律。

## 修订（2026-10-09，设计审查后）

- 专用模型只用于打分任务（见 ADR 0004 修订）。
- 专用模型跑在主控监管的 mlx-lm 工作进程里，不在主控进程里，这样它出故障不会带崩主控，以后也能做到主控重启时不打断 jiu；第一版仍接受"主控重启就重启引擎"（主控退出时工作进程也自行退出），自更新只在安静时刻。
- 专用模型的请求也带请求等级（jiu 的打分是"用户在等"），"交互中"的判定覆盖所有路径，打分请求同样按粗估规则考虑打断后台工作；派发、自动安装、冒烟检查都只引用"交互中"和"安静时刻"这两个判定。
- 上文"施加功耗规则"更正：专用模型只服务"用户在等"的打分请求，功耗档、电池和过热规则对它不起作用；主控对它管的是加载、内存和进程监管。
- jiu 的 580 ms 是独占 GPU 时测的；后台 prefill 正在进行时能否守住，要先实测（DESIGN §13 第 0 项），再决定让路的力度。GPU 争用和模型在哪个进程里跑无关，本决定只是让主控能协调它。
- "只引用这两个判定、不另设计时器"有一个可能的例外：jiu 与后台共存做法 1 的 K 分钟后台接纳窗口（如果实测后采用），它只作用于后台请求的接纳（DESIGN §6）。

## 修订（2026-10-10，jiu 由螺壳输入法取代）

jiu 已由螺壳输入法（luoke-ime）取代，上文和上一段修订里说 jiu 的地方，现在都落在输入法的重排打分上，决定本身不变。和 jiu 相比有两点要注意：

- 输入法的打分更密、更紧：每个键都可能触发一次重排，一次重排逐词做 1–9 次打分，最后一个键之后约 150 ms 内要拿到结果（jiu 是上屏后判断一次，M4 上 p90 580 ms）。专用模型直连、不经派发的理由因此更充分，后台让路的力度要按输入法的数字实测（DESIGN §13 第 0 项）。
- 输入法的打分请求来自它沙盒里的输入法引擎，由输入法的壳转给主控；对主控来说配件只有输入法一个。

## 修订（2026-10-19，顶层 ADR 0013）

上文"主控必须守住不落盘、不显示、不进日志的纪律"的规则不变，理由改写：顶层 ADR 0013 定了本机组件之间不为隐私设限，所以这不是隐私上的自我设限，而是日志和缓存不该是存内容的地方——内容的正本在各工具和记忆里；诊断信息会出本机，必须只含元数据；oMLX 的 SSD 缓存实测命中 0%，关着不亏。以后要做提示缓存或回放时可以放开。
