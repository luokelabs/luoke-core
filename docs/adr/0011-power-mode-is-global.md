# 功耗档管后台工作和本机端点，只有打字和配件里手动点的请求例外

负责人 2026-10-22 定。原来的规则是"功耗档只管后台工作，用户在等的请求永远全速"（DESIGN §6）。定这条规则时，"用户在等"只有两种：配件里点一下等结果，和打字。两种都是几秒钟、量很小，限不限速对 GPU 没什么区别。

本机端点（顶层 ADR 0014 修订）上线后，pi 这类工具的代理循环也走"用户在等"：一跑几十个请求、几分钟，GPU 一直满着。负责人选了静音，看到 GPU 还是跑满，认为功耗档应该是全局的。普通用户心里的"功耗档"也是全局的：macOS 的低电量模式、笔记本的性能模式都连前台一起降。

改为：功耗档管后台工作和本机端点的请求。端点的请求照旧算"用户在等"，排在后台前面、打断后台；但每条做完，下一条要等它用时的同一个倍数（全速 0、均衡 1、静音 3，和后台一样，负责人选的），最多歇 10 分钟。两类请求不管功耗档，永远全速：打字（打分、联想，量小，要毫秒级回应），以及配件里用户手动点了、等着结果的请求（负责人："用户手动操作的还是快一些好"）。

## Considered Options

- **只有静音档管端点，均衡不管**：默认的均衡档下 pi 速度不变。负责人选了和后台一样，图一致。
- **端点限速到每秒多少 token**：做不到，oMLX 不能限速。只能在请求之间歇。
- **功耗档连配件里手动点的请求也管**：一条规则只有打字一个例外，好解释。负责人否了：手动操作要快。

## Consequences

- 默认的均衡档下，pi 这类连着发请求的工具大约慢一半（GPU 约一半时间空着）；静音档约慢到四分之一。要满速就切全速。
- 单条请求生成到一半不会慢下来：一个很长的回答照样满速跑完，歇在它后面。
- 歇的时候请求是挂着等，不是拒绝（拒绝了 pi 会报错）。客户端的超时要比最长的间歇长；间歇封顶 10 分钟。
- 主控日志的端点那一行多记 `waited`（这条等了多久）、`rest_next`（下一条要歇多久）和功耗档。
