# 每个配件版本都要先过评测才能发布

配件每发一个版本（哪怕只改了一句提示词），都要先由实验室用它的评测集在所有现役底座上回放、达到三层及格线，写进配方的"已验证版本"后才能发布；主控只安装已验证的版本。理由：提示词在配件里（ADR 0005），只给"新任务"设关卡挡不住同一个任务换了提示词；只有逐版本验证，"实验室兜底"才覆盖到用户机器上实际在跑的东西，换代前提里的"现行版本"也才有明确含义。代价是改提示词不能"改完就发"，要等实验室的评测跑完（自动化后约几十分钟到几小时）。

## Considered Options

- **只有任务契约变了才评测（给任务升大版本）**：否决，一句改坏的提示词照样会到用户手里。
- **不强制，作为实验室内部纪律**：否决，原因同上。

## Consequences

- 每个配件的发布流程都要加一道 CI 关卡；质量与机器内存无关，可以在一台机器上跑所有底座。
- 换代时，用户机器上的配件太旧会先被更新到在新底座上已验证的版本；维持期内发布的配件版本要在新旧两个底座上都验证。

## 修订（2026-10-09，设计审查后）

- "所有现役底座"改为"各硬件档角色为'现役'的模型分配里、它的任务用到的每个组合"（组合 = 一个模型文件 + 一个引擎包版本），这样只用专用模型的 jiu 也有明确的验证对象。上文的"现行版本"即在新组合上的已验证版本。
- 第一版由负责人手动跑发布脚本：自动判定第 1、2 层；第 3 层用"硬性条目零回退、总分不低于之前已验证的结果减去容差"加逐条差异报告，负责人看过再放行。评测集扩到约 200 条后再换成统计非劣检验；CI 自动关卡以后再做（能跑大底座的只有负责人日常用的机器）。上文"几十分钟到几小时"是未经实测的估计，以 DESIGN §13 第 6 项的实测为准。
- 质量在一台机器上评，再在每代芯片（M1、M4、M5）上回放一个固定子集，核对逐条一致；硬性条目不一致就不发布。
- 延迟不进及格线，而是单独的"延迟要求"：在任务写明的实验室机器上当发布关卡，用户机器上只提示"较慢"。
- 发布车下（ADR 0009），换了引擎包的发布，新配件版本还要在上一版引擎包的组合上验证；上一个引擎包版本的组合在新配方里以"上一版"角色保留到下一次换引擎包的发布，作为引擎包单独回退的落点；不换引擎包的发布不再补验上一版。

## 修订（2026-10-10，jiu 由螺壳输入法取代）

"只用专用模型的 jiu"现在是螺壳输入法：jiu 已由输入法取代，输入法的重排打分同样只用专用模型，验证对象按同一规则确定。

## 修订（2026-10-23，负责人定：内部版评测加「金丝雀」）

出版要验证的东西是"用户机器上实际跑的组合"。之前的做法是：证据里记下配件、主控代码、引擎、评测表、题集；任何一样变了，那一格就重评。主控代码几乎每版都改，所以 10-22、10-23 的几版一条证据都没沿用，每版三档 26 条全评，16 GB 档要 50 多分钟。主控的大部分改动（界面、安装器、出版脚本、配件管理）其实不碰推理。

改为：**只有主控代码变了**（配件、引擎、评测表、题集和语料、配方参数都没变）的格子，不直接重评。每一档先评一条"金丝雀"。评测在温度 0 下是确定的，金丝雀的原始答复和上一版逐字节一样（去掉用时、日期、标签这类每次都变的字段），分数和硬性条目也一样，就说明这次主控改动没影响这一档的推理。这一档其余这类格子沿用上一版的证据，证据里记 `canary`，日志写「金丝雀核过」。有一档不一样，那一档照旧全评。配件或别的条件变了的格子不受影响，照旧重评。

保底三条：

1. **金丝雀挑长提示的任务**：截断、内存重试这类分支，短任务走不到。按这个顺序取这一档开着的第一条：`luoke-mem.topics`、`luoke-mail.thread`、`luoke-mail.triage`、`luoke-mail.cleanup`（`tools/internal_build.py` 的 `CANARY_ORDER`）。
2. **每周至少全评一次**：离上一次全评超过 7 天，这一版就全评。全评过的版本在 `pins.json` 里记 `eval_mode: full`。
3. **beta 和公开版一律全评**，不走金丝雀；内部版也可以用 `--full-eval` 强制全评。

代价：一条任务的答复一样，不保证别的任务也一样。金丝雀挑长提示的任务，加上每周全评，压住这个风险。

## 修订（2026-10-25，金丝雀的两条补充）

实际跑下来补两条，规则本身（逐字节一样才沿用）不变：
- **金丝雀任务在每一档最先跑**：16 GB 测试机（M1）（M1、9B）上，同一个任务如果前面先跑过别的，温度 0 的答复也会差几个字；排在最先、跑在刚起的引擎上，每一版就一致。新旧两版主控实测逐字节一样。
- **只从生成任务里挑**（topics、thread、triage、cleanup）：输入法的 rerank、predict 结果里有"在时限内来不来得及"这类和速度有关的数，逐字节永远对不上。一档里没有可挑的，这一档就全评。
