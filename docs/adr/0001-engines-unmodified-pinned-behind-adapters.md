# 引擎作为不修改的固定版本依赖，通过适配器接入

主控环境里的引擎（第一版：底座用 oMLX，专用模型用进程内的 mlx-lm）一律作为钉住版本、一行不改的依赖来用，只通过它们公开的启动参数、配置和接口来控制；主控为每个引擎写一个适配器，负责把任务层的请求翻译成该引擎的接口、套上底座参数。需要引擎改代码的地方提给上游，不 fork。这样换引擎版本只需要换包、必要时改适配器，主控不必跟着引擎的更新节奏维护一份分叉。

## Considered Options

- **fork oMLX 并按需修改**：能直接补上中断时保留 KV、按请求等级接纳等能力，但要长期追 oMLX 很快的更新节奏（0.7.0rc1 一次就改了性能并悄悄去掉了设置），否决。
- **第一版只用 mlx-lm**：最可控、能真正暂停续做，但失去 MTP（27B 解码约 30 vs 43–81 tok/s）、原生 Bonsai 2 和 oQ 量化，现有证据要全部重测，否决。

## Consequences

- 引擎版本是配方的一部分。升级引擎在代码上可以独立进行，但发布上和换代一样：先在新版本上回放评测集、写进新配方，再由主控下发、做冒烟检查。
- oMLX 是 Apache-2.0，可以随主控再分发（附声明）。在 0.7.0 源码里核实过，不改代码就能锁住：`--base-path` 指向主控环境，只听 127.0.0.1、随机端口，每次启动生成随机 `--api-key`，不传 `--paged-ssd-cache-dir`（SSD 前缀缓存默认关闭），不传 `--mcp-config`。管理面板和 websearch 路由无法关闭，但都要那枚密钥才能访问。
- 引擎暂时做不到的事由主控补位，同时向上游提需求：派发保证同一时间最多一条后台请求在引擎里（oMLX 没有请求优先级）；中断即丢弃重跑（oMLX 中断时丢弃该请求的 KV，见 docs/research/interrupt-and-resume.md）。

## 修订（2026-10-09，设计审查后）

- **更正**：上文"不传 `--paged-ssd-cache-dir` 时 SSD 前缀缓存默认关闭，在源码里核实过"是错的。oMLX 0.7.0 里 `CacheSettings.enabled` 默认为 True，不传参数时缓存目录默认是 `{base_path}/cache`，只有 `--no-cache` 才关闭（`cli.py` 352–368、`settings.py` 373–378）；`hf_cache_enabled` 也默认为 True。初稿被 `--paged-ssd-cache-dir` 的帮助文字误导，设计审查发现了这个错误。现行的启动清单以 DESIGN §5 为准，并且每个引擎包版本都要逐条实测，写进配方的引擎包清单。
- 第一版只有一个**引擎包**：钉住版本、不改代码的 oMLX，连同它自带的 Python 和 mlx，由实验室用自己的 Developer ID 重签并公证（和主控、配件同一个 Team ID）。专用模型不在主控进程里调用 mlx-lm，而是跑在主控监管的 mlx-lm 工作进程里，用引擎包里的 Python。配方里的引擎包版本同时管底座和专用模型两条路，升级引擎包时要回放所有配件的评测集，包括 jiu 的。
- 上文"和换代一样"只指流程（评测 → 写进配方 → 下发 → 冒烟检查），这在第一版不变。第一版新增的是引擎包的单独回退：换了引擎包的发布，新配件版本也要在上一版引擎包的组合上验证；冒烟检查失败或熔断时只退回上一版引擎包（v0 只保留旧底座，引擎没有回退路径）。
- oMLX 自带的内存保护会自己拒绝请求、驱逐模型、在硬压力下中止全部请求。主控用 `--memory-guard-gb` 把自己算出的预算传给它当天花板，并在预算变化时通过管理接口更新；它的这些动作一般按"内存不够"处理，不计入熔断（例外见 DESIGN §12）。
- 向上游提的需求加一项：prefill 块大小可配置（目前最多 2048 token，是"用户在等"的请求被打断时要多等的时间来源）。
- 引擎包的回退条件以 DESIGN §8 为准：任何一次冒烟检查失败（首次，或 macOS 更新后补做的）或熔断，这个引擎包立即停止服务，能退回上一版就退回，否则相关任务暂停。引擎包版本在启动清单变化时也要变。

## 修订（2026-10-10，jiu 由螺壳输入法取代）

文中"包括 jiu 的"评测集，现在指螺壳输入法（luoke-ime）的评测集：jiu 已由输入法取代，升级引擎包时同样要回放它的重排评测。
