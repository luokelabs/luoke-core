# 第一版按发布车发布：主控、配方、配件、引擎包一起发布，用一个发布版本号标识

v0 的设计让配方、配件、引擎包各自独立更新（配方有自己的签名通道，换底座不必发主控），这是为"各方独立发版、用户机器上版本参差"准备的。第一版只有两个实验室自己的配件、一个用户和几位社区测试者，没有这个问题，所以改为发布车：主控、配方、配件、引擎包共用一个发布版本号，一起评测、一起发布；配方放在主控 .app 里，完整性由代码签名和公证保护；主控自更新（Sparkle 一类）后，在安静时刻安装同一版本的配件和引擎包。这省掉了配方签名密钥、独立通道、拒收旧配方和跨版本兼容。配件和引擎包仍各自保留版本号，配方里的发布清单记录这次发布包含哪些版本；引擎包版本在 oMLX、它的 Python、mlx、mlx-lm 或启动清单任一变化时都要变。

## Consequences

- 撤回清单随检查更新一并取回，取到就立即停用，不需要先安装新版本；自动更新开关只管要不要安装新版本。需要核实更新框架是否给更新源本身签名，否则撤回清单另行签名；更新源要保证国内能访问。v1.x 有了独立配方通道后改由它送达。
- 引擎包可以单独回退：换了引擎包的发布，新配件版本也要在上一版引擎包的组合上验证（这几项任务多评一轮），上一个引擎包版本的组合在新配方里以"上一版"角色保留到下一次换引擎包的发布；引擎包冒烟失败或熔断时只退回上一版引擎包，主控保留上一版引擎的适配器。配件新版本只在报告正常之前失败才退回旧包。
- 第一版期间各硬件档的模型文件不变，换模型等 v1.x 的换代流程；唯一的例外是底座或专用模型被撤回后，由下一次发布车带上替换的模型，下载前先征得同意。
- 配方格式第一版就带上版本号、`min_hub_version`、`revoked`、模型分配的角色和预留的签名字段，以后开独立通道时不必改格式。
- 主控不拒收比本地旧的配方，否则用户无法手动装回旧版主控。
- 维持期（是否保留待定）这类为独立发版设计的机制，以及第一次换代之前走不到的换代流程，推到 v1.x（DESIGN §0.2）。
